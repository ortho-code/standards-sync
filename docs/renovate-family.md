# The renovate family — decision record

Part of the [rule-model design record](rule-model.md), split out per family; the contract, the doctrine, the cross-family decisions, and the roadmap live there. Entries are chronological under their original headings.

## Agreed 2026-08-13 (R3, seventh tool) — the renovate family: the extends tier across three JSON grammars

Promoted from the roadmap's candidate list (recorded 2026-08-11) as the strongest of the four: a native `extends` tier (shareable presets) makes it Tier A, the cheapest mechanism there is, over the JSON writer the composer.json family built. Scoped at promotion: the `renovate.json5` rule is part of the family's first cut — both per-format rules ship together, not a JSON-only first slice with json5 deferred. This entry records the verified config surface the design phase opens with, and the open questions it left.

**Verified facts (renovate 44.27.0, the release tag current on 2026-08-13 — read from the tool's source at that tag and probed live through the distributed `renovate-config-validator`, never from recall):**

- **The candidate list is brace-expanded and ordered** (`lib/config/app-strings.ts`): `renovate.json`, `renovate.jsonc`, `renovate.json5`, the same triple under `.github/` and `.gitlab/`, `.renovaterc`, `.renovaterc.json`, `.renovaterc.jsonc`, `.renovaterc.json5`, `package.json`. The `.github/` and `.gitlab/` triples are filtered to the matching platform, and every other platform (except a bare `local` run) gets `.<platform>/renovate.json{,c,5}` appended after `package.json` — on Bitbucket, `.bitbucket/renovate.json` and its siblings. Self-hosted `configFileNames` entries are checked before all of these. The roadmap's candidate bullet predates this read: `.jsonc` variants exist too, so three grammars are in play, not two — and the user docs still list the set without them, so the source is the authority.
- **The first existing candidate wins, silently** (`detectConfigFile()`, `lib/workers/repository/init/merge.ts`): the repo's file list is scanned in candidate order and the first hit is the config; nothing warns when several exist, so a `renovate.json` shadows a `renovate.json5` sitting beside it. `package.json` counts only when it carries a `renovate` key, logged with a deprecation warning and documented as scheduled for removal.
- **Grammar splits on the `.json5` extension alone** (`lib/config/parse.ts`, `lib/util/common.ts`): `.json5` is parsed with `JSON5.parse` — full JSON5. Every other candidate, `renovate.json` included, takes a JSONC-lenient path: comments and trailing commas are tolerated, duplicate keys are a hard config error in bot runs (`json-dup-key-validator`), and content that is invalid JSONC but valid JSON5 still parses with a logged warning naming its future removal. Probed against the distributed validator: comments plus a trailing comma in `renovate.json` validate clean; unquoted keys and single quotes in `renovate.json` validate with that deprecation warning; a commented `renovate.json5` validates clean. Strict JSON sits inside every candidate's accepted grammar, and an empty config file counts as `{}`.
- **Duplicate keys diverge between the two run paths**: the bot's repo path refuses them — in the JSONC grammar only, since `JSON5.parse` has no duplicate check and last-wins silently — while the standalone `renovate-config-validator` parses without the duplicate check and accepted a doubled `extends` key in the probe.
- **`extends` merges left-to-right, and the file's own keys win** (`resolveConfigPresets()`, `lib/config/presets/index.ts`): presets resolve recursively — a preset's own `extends` resolves before the next sibling — each merging over the previous via `mergeChildConfig`, and the config that declared the `extends` merges last. The merge is per-option child-wins, except options declared `mergeable` (`packageRules` among them), which combine instead of replace. So the org entry's *position* in the `extends` array carries semantics, a consumer's own keys always override the preset, and `ignorePresets` is the consumer-native opt-out for an inherited preset.
- **Preset sources are a fixed loader map** — `github`, `gitlab`, `gitea`, `forgejo`, `http`, `local`, `npm` (`lib/config/presets/index.ts`). There is no `bitbucket>` prefix; `local>` resolves through the current platform's raw-file fetch and explicitly serves bitbucket, bitbucket-server, azure and gerrit (`lib/config/presets/local/index.ts`), so a preset hosted on the org's own forge is reachable as `local><workspace>/<repo>` from repos on the same platform; `http>` and a public `github>` repo are the cross-platform alternatives. A bare `local` platform run supports no local presets at all. `extends` is repo config's only composition mechanism: `parsePreset()` (`lib/config/presets/parse.ts`) routes every non-internal entry to these sources — explicit prefixes, a bare URL to `http`, `@scope` and bare names to `npm`, a bare `owner/repo` spelling implicitly to `local` — and no file-path source exists, so repo config can never include a file from the repo's own tree; nothing composer-delivered under `vendor/` is reachable, since the bot reads the committed tree and never runs composer. Bot-side injection (self-hosted global config, `inheritConfig`) is the administrator's channel, not the repo's — org governance outside file-sync reach, like branch protection in the composer-family flag.
- **A preset repo serves `default.json`** (`lib/config/presets/util.ts`): the `renovate.json` fallback is deprecated with a warning; an explicitly named preset file may keep a `.json`, `.jsonc` or `.json5` extension — anything else gets `.json` appended — so the org preset itself defaults to a strict-named `default.json`.
- **Onboarding creates, and only when nothing exists**: with no config found, the bot opens its "Configure Renovate" PR adding `onboardingConfigFileName` (default `renovate.json`; a value outside the candidate list falls back to the first candidate — `getDefaultConfigFileName()`, `lib/workers/repository/onboarding/common.ts`). An existing config is never touched by onboarding.
- **The competing writer is config migration, opt-in and whole-file** (`configMigration`, default `false`, experimental; `lib/workers/repository/config-migration/branch/migrated-data.ts`): its migration PR re-serializes the parsed config — `.json5` through `JSON5.stringify`, which discards every comment; the other names through jsonc-weaver's `weave(raw, migrated)`, which preserves them, with `JSON.stringify` as the fallback; indentation is detected with two spaces as the default and a trailing newline is ensured. Renovate's own writer treats the json5 grammar *worse* than the lenient json one — comment-carrying json5 configs lose their prose to a migration PR.
- **The standalone validator checks every existing candidate, not the first** (`lib/config-validator.ts`): all present candidate files plus a `package.json` `renovate` key validate independently and any failure exits 1 — the natural CI-side check for consumer repos, and a behavioural mismatch with the bot's first-wins read worth remembering when a repo carries two files.

**Open questions for the design phase, recorded at the agreed stage:**

- **Cross-format ambiguity has no engine answer yet.** `renovate.json` and `renovate.json5` are separate per-format rules under the multi-format decision, so the same-side ambiguity refusal — which lives inside one `FileTarget`'s candidate list — never sees the pair; yet Renovate reads only the precedence winner, so syncing both would leave one file's standard as dead text. The verified precedence order above is the material to design with.
- **The JSONC leniency cuts across the format split.** A consumer's `renovate.json` may legally carry comments today, which a strict-JSON read (`JsonObjectWriter` validates the document up front) refuses loudly rather than edits. Whether the json rule tolerates that grammar, refuses it, or the family points such repos at the json5 rule is a design choice. *(Closed 2026-08-13 — refusal; see the decided note below.)*
- **JSON5 makes the enforced-comment feature applicable to a JSON-family member for the first time** — the 2026-08-04 decision excluded JSON for having no comments. Whether the json5 rule adopts it is a design choice, not a given.
- **The backend re-assessment is owed** (the standing rule in [conventions.md](conventions.md); the composer-family entry names renovate as its trigger): a JSON5-capable writer is new `Formats/` work either way, and JSON5's comments re-import exactly the comment-boundary corruption class the neon writers had to fix — the hand-rolled-versus-parser-backed question is live again with different weights.
- **Org-shaped choices needing worked examples:** which candidates each rule's target declares (the platform-dir triples, `.renovaterc` and its dotted variants — and whether the deprecated `package.json` key is out of scope by construction); and the org entry's spelling, since `local>` reaches only same-platform consumers while `github>`/`http>` cross platforms.

### Decided 2026-08-13 — first-cut refinements, from review of this entry

- **The `.jsonc` rule is deferred.** The jsonc names exist only in the tool's code, not its documentation; the first cut ships the json and json5 rules, and a jsonc rule is a purely additive third per-format member should a real repo bring the need. The jsonc candidate names stay in the record regardless: the cross-format design must account for every name that can shadow or be shadowed — a created `renovate.json` outranks an existing `renovate.jsonc`, so creation must not produce dead text.
- **The json rule refuses JSONC-lenient content.** A `renovate.json` carrying comments or trailing commas refuses at plan time — fail-loud over silent tolerance, aligned with upstream's own strictness direction (the json5-in-json fallback is already deprecated) — with a message naming both exits: make the file strict JSON, or rename it to `renovate.json5` where the json5 rule takes over. Revisit if comment-carrying `renovate.json` files prove common. Mechanically the JSON writer's up-front document validation already refuses non-JSON; the design phase owes only the tool-named message.
