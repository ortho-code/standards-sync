# The renovate family — decision record

Part of the [rule-model design record](rule-model.md), split out per family; the contract, the doctrine, the cross-family decisions, and the roadmap live there. Entries are chronological under their original headings.

## Agreed 2026-08-13 (R3, seventh tool) — the renovate family: the extends tier across three JSON grammars

Promoted from the roadmap's candidate list (recorded 2026-08-11) as the strongest of the four: a native `extends` tier (shareable presets) makes it Tier A, the cheapest mechanism there is, over the JSON writer the composer.json family built. Scoped at promotion: the `renovate.json5` rule is part of the family's first cut — both per-format rules ship together, not a JSON-only first slice with json5 deferred. This entry records the verified config surface the design phase opens with, and the open questions it left.

**Verified facts (renovate 44.27.0, the release tag current on 2026-08-13 — read from the tool's source at that tag and probed live through the distributed `renovate-config-validator`, never from recall):**

- **The candidate list is brace-expanded and ordered** (`lib/config/app-strings.ts`): `renovate.json`, `renovate.jsonc`, `renovate.json5`, the same triple under `.github/` and `.gitlab/`, `.renovaterc`, `.renovaterc.json`, `.renovaterc.jsonc`, `.renovaterc.json5`, `package.json`. The `.github/` and `.gitlab/` triples are filtered to the matching platform, and every other platform (except a bare `local` run) gets `.<platform>/renovate.json{,c,5}` appended after `package.json` — on Bitbucket, `.bitbucket/renovate.json` and its siblings. Self-hosted `configFileNames` entries are checked before all of these. The roadmap's candidate bullet predates this read: `.jsonc` variants exist too, so three grammars are in play, not two — and the user docs still list the set without them, so the source is the authority.
- **The first existing candidate wins, silently** (`detectConfigFile()`, `lib/workers/repository/init/merge.ts`): the repo's file list is scanned in candidate order and the first hit is the config; nothing warns when several exist, so a `renovate.json` shadows a `renovate.json5` sitting beside it. `package.json` counts only when it carries a `renovate` key, logged with a deprecation warning and documented as scheduled for removal.
- **Grammar splits on the `.json5` extension alone** (`lib/config/parse.ts`, `lib/util/common.ts`): `.json5` is parsed with `JSON5.parse` — full JSON5. Every other candidate, `renovate.json` included, takes a JSONC-lenient path: comments and trailing commas are tolerated, duplicate keys are a hard config error in bot runs (`json-dup-key-validator`), and content that is invalid JSONC but valid JSON5 still parses with a logged warning naming its future removal. Probed against the distributed validator: comments plus a trailing comma in `renovate.json` validate clean; unquoted keys and single quotes in `renovate.json` validate with that deprecation warning; a commented `renovate.json5` validates clean. Strict JSON sits inside every candidate's accepted grammar, and an empty config file counts as `{}`.
- **Duplicate keys diverge between the two run paths**: the bot's repo path refuses them — in the JSONC grammar only, since `JSON5.parse` has no duplicate check and last-wins silently — while the standalone `renovate-config-validator` parses without the duplicate check and accepted a doubled `extends` key in the probe.
- **`extends` merges left-to-right, and the file's own keys win** (`resolveConfigPresets()`, `lib/config/presets/index.ts`): presets resolve recursively — a preset's own `extends` resolves before the next sibling — each merging over the previous via `mergeChildConfig`, and the config that declared the `extends` merges last. The merge is per-option child-wins, except options declared `mergeable` (`packageRules` among them), which combine instead of replace. So the org entry's *position* in the `extends` array carries semantics, a consumer's own keys always override the preset, and `ignorePresets` is the consumer-native opt-out for an inherited preset.
- **Preset sources are a fixed loader map** — `github`, `gitlab`, `gitea`, `forgejo`, `http`, `local`, `npm` (`lib/config/presets/index.ts`). There is no `bitbucket>` prefix; `local>` resolves through the current platform's raw-file fetch and explicitly serves bitbucket, bitbucket-server, azure and gerrit (`lib/config/presets/local/index.ts`), so a preset hosted on the org's own forge is reachable as `local><workspace>/<repo>` from repos on the same platform; `http>` and a public `github>` repo are the cross-platform alternatives. A bare `local` platform run supports no local presets at all. `extends` is repo config's only composition mechanism: `parsePreset()` (`lib/config/presets/parse.ts`) routes every non-internal entry to these sources — explicit prefixes, a bare URL to `http`, `@scope` and bare names to `npm`, a bare `owner/repo` spelling implicitly to `local` — and no file-path source exists, so repo config can never include a file from the repo's own tree; nothing composer-delivered under `vendor/` is reachable, since the bot reads the committed tree and never runs composer. Bot-side injection (self-hosted global config, `inheritConfig`) is the administrator's channel, not the repo's — org governance outside file-sync reach, like branch protection in the composer-family flag.
- **A preset repo serves `default.json`** (`lib/config/presets/util.ts`): the `renovate.json` fallback is deprecated with a warning; an explicitly named preset file may keep a `.json`, `.jsonc` or `.json5` extension — anything else gets `.json` appended — so the org preset itself defaults to a strict-named `default.json`.
- **Onboarding creates, and only when nothing exists**: with no config found, the bot opens its "Configure Renovate" PR adding `onboardingConfigFileName` (default `renovate.json`; a value outside the candidate list falls back to the first candidate — `getDefaultConfigFileName()`, `lib/workers/repository/onboarding/common.ts`). An existing config is never touched by onboarding.
- **The competing writer is config migration, opt-in and whole-file** (`configMigration`, default `false`, experimental; `lib/workers/repository/config-migration/branch/migrated-data.ts`): its migration PR re-serializes the parsed config — `.json5` through `JSON5.stringify`, which discards every comment; the other names through jsonc-weaver's `weave(raw, migrated)`, which preserves them, with `JSON.stringify` as the fallback; indentation is detected with two spaces as the default and a trailing newline is ensured. Renovate's own writer treats the json5 grammar *worse* than the lenient json one — comment-carrying json5 configs lose their prose to a migration PR.
- **The standalone validator checks every existing candidate, not the first** (`lib/config-validator.ts`): all present candidate files plus a `package.json` `renovate` key validate independently and any failure exits 1 — the natural CI-side check for consumer repos, and a behavioural mismatch with the bot's first-wins read worth remembering when a repo carries two files.

**Open questions for the design phase, recorded at the agreed stage:**

- **Cross-format ambiguity has no engine answer yet.** `renovate.json` and `renovate.json5` are separate per-format rules under the multi-format decision, so the same-side ambiguity refusal — which lives inside one `FileTarget`'s candidate list — never sees the pair; yet Renovate reads only the precedence winner, so syncing both would leave one file's standard as dead text. The verified precedence order above is the material to design with.
- **The JSONC leniency cuts across the format split.** A consumer's `renovate.json` may legally carry comments today, which a strict-JSON read (`JsonObjectWriter` validates the document up front) refuses loudly rather than edits. Whether the json rule tolerates that grammar, refuses it, or the family points such repos at the json5 rule is a design choice. *(Closed 2026-08-13 — refusal; see the decided note below.)*
- **JSON5 makes the enforced-comment feature applicable to a JSON-family member for the first time** — the 2026-08-04 decision excluded JSON for having no comments. Whether the json5 rule adopts it is a design choice, not a given.
- **The backend re-assessment is owed** (the standing rule in [conventions.md](conventions.md); the composer-family entry names renovate as its trigger): a JSON5-capable writer is new `Formats/` work either way, and JSON5's comments re-import exactly the comment-boundary corruption class the neon writers had to fix — the hand-rolled-versus-parser-backed question is live again with different weights.
- **Org-shaped choices needing worked examples:** which candidates each rule's target declares (the platform-dir triples, `.renovaterc` and its dotted variants — and whether the deprecated `package.json` key is out of scope by construction); and the org entry's spelling, since `local>` reaches only same-platform consumers while `github>`/`http>` cross platforms.

### Decided 2026-08-13 — first-cut refinements, from review of this entry

- **The `.jsonc` rule is deferred.** The jsonc names exist only in the tool's code, not its documentation; the first cut ships the json and json5 rules, and a jsonc rule is a purely additive third per-format member should a real repo bring the need. The jsonc candidate names stay in the record regardless: the cross-format design must account for every name that can shadow or be shadowed — a created `renovate.json` outranks an existing `renovate.jsonc`, so creation must not produce dead text.
- **The json rule refuses JSONC-lenient content.** A `renovate.json` carrying comments or trailing commas refuses at plan time — fail-loud over silent tolerance, aligned with upstream's own strictness direction (the json5-in-json fallback is already deprecated) — with a message naming both exits: make the file strict JSON, or rename it to `renovate.json5` where the json5 rule takes over. Revisit if comment-carrying `renovate.json` files prove common. Mechanically the JSON writer's up-front document validation already refuses non-JSON; the design phase owes only the tool-named message.

## Designed 2026-08-13 — one candidate-aware rule across both grammars; the `AppliesAtPath` seam

The design phase, run the same day over the verified surface above. The finding that shaped everything: a pure rule sees only its own file's content, so no two-rule split can express "create `renovate.json` unless `renovate.json5` exists" — and getting that wrong produces dead text, because Renovate silently reads only the precedence winner (a json rule creating beside a consumer's `renovate.json5` kills that entire config). All names therefore live in **one `FileTarget`**, where resolution sees everything at once and the existing same-side refusal already covers the confused repo — `renovate.json` beside `renovate.json5` refuses today with the standing "remove all but one" message, zero new engine code. What is genuinely new is that the rule must know *which candidate resolved*, because grammar hangs on the filename.

**The decisions:**

- **One rule, `RenovateExtendedPreset`**, target carrying all names, grammar dispatched on the resolved name — one small, visible match owned by the family: `.json5` means JSON5, every other name means strict JSON, and a resolved `.jsonc` name refuses (the deferral above), as does JSONC-lenient content in a strict-JSON name. One concern is one rule identity: `withoutRule(RenovateExtendedPreset::class)` disables the whole concern. This revises the promotion scope's *phrasing* — "both per-format rules" became one rule spanning both grammars — while the substance, json5 fully in the first cut, stands. Rejected: two naive per-format rules (the dead-text creation hazard above); two rules sharing the full candidate list and each abstaining unless the resolved name is theirs (needs the same seam, splits one concern across two disable identities, duplicates the name-list knowledge); a content-sniffing single rule (grammar from content alone cannot distinguish a commented `renovate.json` from json5, so it cannot implement the decided refusal).
- **The seam: `AppliesAtPath`, an opt-in interface beside `ExplainsDrift`** — `applyAt(Path $path, ?string $content): ?string`, called by the engine's fold in place of `apply()` for rules that implement it; the resolved target is already in hand there, so the dispatch is one line. `apply()` delegates to `applyAt()` with the first candidate, documented as "no path means the creation candidate's grammar". Purity holds: the path is data passed in, never filesystem access. Deliberately **not** retrofitted onto other families — their candidates are same-grammar name variants, and resolved-path ignorance is a feature of the pure-transform contract, not a gap. One recorded future adopter: `ManagedBlockRule`'s mixed-comment-syntax refusal, whose R0 note named "a per-candidate contract seam" as its mechanism — the seam now exists; adoption still waits for a real case. Rejected: a plan-time per-candidate rule factory (a new pipeline concept with a target-before-rule chicken-and-egg; the parked per-root factory's cousin, far heavier than one interface); widening `apply()` itself (a widened parameter breaks every implementor — the R0 asymmetry rule).
- **The candidate list is renovate's static set**: `renovate.json{,c,5}`, the same triples under `.github/` and `.gitlab/`, `.renovaterc` and `.renovaterc.json{,c,5}`. The jsonc names are candidates that refuse when resolved, so a repo carrying one is never shadowed by a created root file. `package.json` is out by construction (deprecated upstream, scheduled for removal). The dynamic platform directories (`.bitbucket/…` and kin) are deferred until a real consumer repo carries one — the R0-recorded optional constructor override is the ready mechanism. Residual, stated: the engine is forge-blind, so a lone `.github/renovate.json` is synced even where the platform filter would ignore it — honoring the file's evident intent beats creating a root file that would kill it on the matching forge.
- **The org chooses the creation format: `createAs:`, a `RenovateConfigFormat { Json, Json5 }` enum defaulting to `Json`** (renovate's own onboarding default). The engine fact this rides on, recorded here because the design leans on it: since the dist-policy rewrite, candidate *order* matters only for creation — a lone existing file wins whatever its name, several existing files refuse — so the preference is expressed by `RenovateConfigFile::target(createAs:)` putting the preferred name first, with no engine change. Consequence, stated plainly: a repo that already has `renovate.json` is synced there even under a json5-preferring org; the repo renames once if it wants json5 — the dist decision's rename-once stance. The enum is legitimate under the strong-typing convention: it is the closed set of grammars this family writes, not renovate's open surface. The `preset:` value stays a validated primitive (non-empty, one line) for exactly the opposite reason. Rejected: a first-class family-settings holder ("FamilyRule") — with one rule the family's settings collapse onto its constructor, shared per-tool knowledge already has a home in the config-file class (the `PhpStanConfigFile` pattern), and the first-class rule-family concept stays parked with its recorded trigger (family-level disabling or reporting).
- **The entry appends.** Presets merge left-to-right and the file's own keys win, so appending makes the org preset the strongest preset while the consumer keeps both native escape hatches (`ignorePresets`, own keys) — and every import family appends. Entry match is decoded string equality, so spellings match.
- **Writers.** `JsonObjectWriter` gains `ensureListEntry()` — the JSON sibling of `YamlListWriter::ensureEntry()`; the existing `writeList()` owns a list wholesale, which must not clobber consumer entries. A new `Formats/Json5/Json5ListWriter` handles the other grammar: comment- and quote-aware scanning (`//` and `/* */`, single- and double-quoted strings with escapes, unquoted keys, trailing commas), decoded comparisons, insertion copying sibling entry style. The backend re-assessment every new `Formats/` member owes was run: no position-aware JSON5 parser exists in PHP — colinodell/json5 (the ecosystem's parser, active, decode-only `json5_decode()`) exposes no positions — so hand-rolled stands for the seventh member; the parser joins require-dev to power `Testing/Validation/Json5Validator`, fail-loud per the 2026-08-12 revision. JSON5's comments re-import the comment-boundary corruption class the neon writers were bitten by; the quote-aware lessons port from birth.
- **The enforced comment is adopted at birth — the first list-writer adoption of the 2026-08-04 pattern.** An optional `comment:` on the rule, written and enforced as a trailing comment on the entry line, json5 only by format capability — a strict-JSON config carries the standard unexplained, the XML verdict's analog, with `ExplainsDrift` covering it. Caveat recorded and accepted: renovate's own opt-in config-migration PR strips every json5 comment (`JSON5.stringify`, see the facts above), and the next sync re-adds ours — "enforced like the value" working as decided.
- **Reaffirmed on request: rules keep knowing their writers.** Asked at this design: should a rule not know which writer it uses? That is the R0 "what/how split" and the R2 "generic rule + applier registry" rejection — a dispatcher would only rediscover what the target already declares, and the hardcoded pairing is what makes cross-format mismatches inexpressible. The decided decoupling level stands one layer down: rules depend on the `Formats/` API only (deptrac-enforced), so backend swaps stay invisible; the renovate rule's grammar dispatch is family knowledge in one visible place, not a general mechanism. Held with a named revisit trigger (same discussion): the question returns when a tool family genuinely spans disparate formats (yaml / php / xml — the Symfony shape the multi-format decision anticipates); whether the rule remains the place that states the format choice, or another layer earns it, is then re-examined against the real cases.

**Build scope (phase 6):**

1. `Core/Rule/AppliesAtPath` and the one-line dispatch in `Engine::foldFile()`.
2. `JsonObjectWriter::ensureListEntry()`; `Formats/Json5/Json5ListWriter`; `Testing/Validation/Json5Validator` with colinodell/json5 in require-dev.
3. `Rules/Renovate/`: `RenovateConfigFile` (the target and the creation-format ordering), `RenovateConfigFormat`, `ExtendedPreset/RenovateExtendedPreset` (`preset:`, `createAs:`, `comment:`; `ExplainsDrift`).
4. Fixtures per the behaviour-catalog rule: created-from-nothing in each format; entry appended; `extends` created in an existing config; in-sync byte-identical; the json5 set (append preserving comments, single-quote and unquoted-key files, comment enforced and re-added); refusals as integration tests per the delete-refusal precedent (lenient json, a resolved jsonc name, both formats existing); a json5-only repo syncing json5 as a resolution scenario; the org family fixture. Within-phase details flagged: created-file indent width, sibling quote-style copying, non-string array entries.
5. Docs riding the build: the roadmap's Next entry, the promotion bullet's revision note, and the R0 candidate-note cross-reference to this seam.

Org wiring follows as phase 7: the preset repo (`default.json` in the org package's own repository, a `local>` entry), both test consumers' live loops, and the scenario-branch change loop.

**Built 2026-08-13**, in the five steps above; all three suites and deptrac green, the new classes covered by the existing directory collectors. What the build settled beyond the design:

- **The flagged within-phase details:** a created config uses the format layer's shared four-space default — renovate re-detects indentation per file, so cross-format consistency inside `Formats/` won over renovate's own two-space habit; insertion copies the sibling entries' quote style (`renderLike`) and the sibling member's key spelling including bare identifiers (`renderKeyLike`), falling back to double quotes; non-string list entries never match and are left untouched.
- **Creation mechanics:** the json5 writer owns creation end to end (empty content becomes the document, trailing newline included); the json side seeds `"{}"` in the rule and appends the newline there, since `ensureListEntry` edits existing text byte-preservingly.
- **The refusals live at the rule** (`assertStrictJson` and the jsonc check in `applyAt()`, with the tool-named messages), so the JSON writer's generic validation never fires in practice; they are pinned in the rule's unit test — apply-level behaviour needs no fold — while the both-formats refusal and lone-file-wins resolution are pinned in the `TargetResolver` integration test against the family's real target.
- **The comment-position boundary:** an entry that does not end its line (a one-line list) carries no comment — the json5 analog of the XML verdict, pinned by a unit case; a deviating spelling of the canonical comment normalizes as collateral of enforcement, never as a reason to edit.
- **The validator:** colinodell/json5 v3.0.0 in require-dev; its `SyntaxError` extends `JsonException` (verified from the installed source), so `Json5Validator` catches exactly what `JsonValidator` does.
- **Two corruption-class defects the self-review caught, fixed with pinned regressions:** the json5 writer's line-anchored insertion landed the new entry past a closing bracket sharing the last entry's line (list and object member alike — both now append inline there), and a comma on a later line was mistaken for the trailing-comma style, dropping the separator between the last and the new entry — a leading-comma list now stays valid.
- Seven scenario fixtures: creation in each format (the json5 one annotated), the entry appended, the list created, in-sync byte-identical, the json5-only repo synced in place with nothing created, and the compliant entry gaining the enforced comment.

**Org wiring 2026-08-13** — the family's closing phase. The consuming org ships its preset as `default.json` at its package repository's root: the renovate bot fetches it over the forge API, never from a composer install, making the preset the first shared artifact an org composer package cannot deliver — the repository doubles as the preset home, and the root is where renovate's own preset convention looks. The org declares the rule with `createAs: Json5` and an enforced comment, spells the entry `local><workspace>/<repo>` (same-forge consumers), and pins the preset file's parseability in its own suite — a broken preset would fail every consumer's renovate run at once. Verified live in both test consumers: the update-path consumer created the annotated `renovate.json5`, a second check reported everything in sync, and the result was committed as its new baseline; the adoption-path consumer created the same file inside its full adoption diff — arriving through the second-tier package's `include()`, exercising the additive layering decision — and was reset to its pre-sync seed. The change loop over the three scenario branches, each rebased onto the moved baseline: the dist-local branch holds (exit 0, the shadowing note, in sync — the new standard rode in through the rebase, no re-baseline needed), and both same-side refusal branches still render their committed messages with non-zero exits.
