# Roadmap

What is ahead, with each item's trigger. The completed trail — everything already built, with dates and reasoning — is [the decision record's sequence](history/rule-model.md#sequence).

## Before the first v1 tag

- **The BC-surface audit**: per class, mark what is API and what is internal, before any compatibility promise is made. Until then the release line is v0.x without a promise — see [release status](distribution.md#release-status) and the contract-first/never-first split in [conventions.md](conventions.md).

## Candidate tool families

The next family is picked from this list rather than from memory; nothing here is designed, and every config surface is unverified — a design phase opens by reading the tool's own source.

- **`Dockerfile`** — needs no engine work: it is comment-bearing, so `ManagedBlock` handles it today and the whole family is org authoring. Recorded because "already possible" is easy to miss.
- **`compose.yaml`** — waits on nothing technically (the YAML writer exists), but `compose.override.yaml` is the record's one named example of genuine multi-file merging, parked as out of scope — picking this family forces that decision open. Not a casual pick.
- **Release workflow + changelog** — the workflow half needs no engine work, like `Dockerfile`, and a standard already ships it: a tag-driven release workflow synced as a managed block, with the release notes extracted from the tag's changelog section (this repository's own release mechanism is the worked example). The **changelog half does** need engine work, and the earlier form of this entry was wrong to bundle them: nothing here can seed a `CHANGELOG.md`, because the one-shot seeds are all tool-specific rules and a managed block is wrong for a file of human prose that must not carry markers. What is missing is a generic seed-if-absent rule; its trigger is the first consumer for which starting a changelog by hand is friction rather than a one-line chore.

## Deferred, with recorded triggers

Each of these is designed as far as its entry records and waits for its trigger; the entries hold the reasoning.

- **A managed block has no extension point, and how much that hurts depends on the format.** A consumer can accept the block, write outside it, or disable the rule — there is nothing in between. In line-oriented files that is enough, because concatenation *is* composition: a `.gitignore` or `.editorconfig` keeps working when a repo adds its own lines after the block, and the two compose by the format's own rules. In a structured single-document format it is not: a CI workflow's block effectively owns the whole file, since appending a second top-level mapping after it is invalid YAML, so a repo needing one extra step in that job has no route short of disabling the rule — and disabling is all-or-nothing, because one rule identity covers every block the standard ships. The same applies to any JSON or single-document YAML artifact a block might carry. Directions when this is picked up: let a block declare named insertion points a consumer fills; teach `ManagedBlock` per-target composition so a structured format merges rather than concatenates (this is the multi-file-merge question the compose.yaml candidate also forces); or leave the mechanism alone and treat it as an authoring rule — a block-delivered workflow should be a *reusable* one that consumers call with their own steps, which needs no engine work at all. Merging contributions to one list, which composer scripts do since 2026-09-29, is the shape the per-target direction would take for a job's list of steps. Trigger: the first consumer that needs a variation and is told to disable the rule instead.
- **Compatibility with output earlier versions already wrote.** The invariant in [architecture.md](architecture.md) states the property: recognition is matching against the *current* rendering, nothing records what was written before, and nothing retracts — so a rendering change appends a duplicate beside the stale original instead of updating it. Every in-place rule sits on this, not just managed blocks: the marker grammar, the verbatim-matched import entries (`EcsBaseSet`, `RectorBaseSet`, the phpstan and deptrac imports, the renovate preset entry), and the paths rendered inside them, which an org package can move without touching the engine at all. The 0.2.0 marker change is the worked example — a two-character edit that became a breaking release with a hand migration across 21 files. Directions, in rising cost and coverage: match structurally rather than on the fully rendered line, so cosmetic changes stop being breaking; have matchers also recognise a recorded list of superseded forms and rewrite them on the next sync, which repairs what is already in the wild at the cost of carrying that list; or the state file below, which is the general answer and covers removal too. Whichever is chosen belongs in the v1 BC-surface audit. Trigger: the next change to any rendered output, or the first outside consumer — whichever comes first, because after either one a break stops being cheap.
  The state-file direction exists since 2026-09-29 for rules contributing to a list (see the next entry); marker decoration and the value rules stay on the coupling.
- **The import-tier rules as list contributions.** `PhpStanIncludedRuleset`, `RectorBaseSet`, `EcsBaseSet`, `DeptracImportedDepfile` and `RenovateExtendedPreset` each add one entry to a list and never retract it, so moving a distributed template or renaming a preset leaves the old entry beside the new one in every consumer.
  Adopting `ContributesToList` turns that into an ordinary sync: the lock records the rendered entry, and a changed one is retracted; nothing changes for an org author.
  Each list writer involved needs a way to take an entry out: `NeonListWriter`, `FluentChainWriter`, `YamlListWriter` and `Json5ListWriter` only ensure entries today, while `JsonObjectWriter` can already read and rewrite a list, which is how `ComposerScript` retracts.
  Trigger: none needed — it is the next item; at the latest, the next change to a rendered import entry.
- **Removing a whole list, or what a dropped rule wrote** — the lock (built 2026-09-29) retracts entries a contribution stops declaring, but a list nothing contributes to any more only drops out of the lock and stays in the file, since no rule is left that knows how to edit it, and rules that are not list contributions record nothing at all. Trigger: manual cleanup proves a burden. Marker blocks carry their own provenance, so they never need this.
- **A delete branch** (`ChangeKind::Delete`, a delete-capable filesystem port) — whole-file removal is refused until a real need arrives; content-level enforce-absence needs nothing special today.
- **Per-instance rule identity** (class + target path) — trigger: a real case where disabling by class is too coarse. The shape to weigh when it arrives: identity as (class, resolved target) reads naturally for the file-targeting rules but does not separate two `ComposerScript`s, which share a target and differ by name — so either identity comes from the rule itself (a method on the contract, which every rule must then implement) or from the declaration site (an optional label passed at construction, which costs nothing for rules that never need it). The second keeps the contract untouched and is the cheaper first cut. It came close on 2026-08-28 and then dissolved, which is worth recording: composer puts a *dependency's* binaries on the script PATH and never the root package's own, so this repository — which ships the tool — could not run a standard's `standards-sync sync --check` script by its bare name, and disabling only that one script would have needed identity per instance. The fix was not disabling anything: a `post-install-cmd` links the package's own binary into the bin directory, so a package that ships a tool can consume its own standard unchanged. The same coarseness still applies to `ManagedBlock`, where one identity covers every block a standard ships (see the block-extension-point entry above).
- **A declared composer command cannot be varied, and the aggregate is why.** `ComposerScript` matches a declared command exactly, so a consumer needing an argument on it — a resource flag, a repo-specific config path — cannot add one: the edited command counts as the project's own, and the next sync inserts the declared one back beside it, so both run. Neither existing route closes it. A consumer can declare its own script calling the declared one, and composer passes arguments through such a reference (verified: `["@app-phpstan --memory-limit=1G"]` appends the argument, transitively through a calling aggregate too) — but the standard's own aggregate calls the declared name, so CI still runs the command without it. Per-instance rule identity, deferred above, does not help either: the aggregate's `@`-references make the scripts a coupled set, so dropping one declared script leaves the aggregate calling a script that no longer exists, which composer skips with a message and exit 0 (verified 2026-09-28).

  **Routes to weigh, none chosen.** Listed so the design pass starts from a list rather than from memory; it opens by researching them — composer's own behaviour read from its source or probed, per the verify-don't-recall rule — and may well find shapes not named here.

  1. *Prefix instead of equality, opt-in per script*: a declared command is enforced as `$actual === $declared || str_starts_with($actual, $declared . ' ')` — the space mandatory, or `analyse` matches `analyse-nothing` — per command with the list length fixed, so a consumer appends arguments and never a step. Opt-in is the point: the standard allows an environmental flag on the analyser and keeps `--level` out of reach, and the default stays the recorded contract rather than loosening every consumer silently. Cheapest of these, and suffix-only: a wrapping prefix (`php -d memory_limit=1G vendor/bin/…`) still needs a wrapper script.
  2. *A named slot in the declared value* — `phpstan analyse {extra}`, the engine owning the fixed parts and the consumer owning the slot. The generalisation of the block-extension-point entry above, from line-oriented blocks to values; heavier, but one mechanism for both.
  3. *Presence instead of content*: a sibling rule enforcing that a named script exists and runs the tool, with the standard owning only the aggregate that calls it. Moves the guarantee from "what it runs" to "that it runs", which is a doctrine change, not just a mechanism.
  4. *Fix the coupling rather than the value*: per-instance identity plus an aggregate that tolerates a disabled member, so opting one script out stops breaking the aggregate. Attacks the reason the existing opt-out fails instead of loosening enforcement.
  5. *Composer's own seams* — `@putenv` entries and argument-passing references — as the delivery mechanism for a variation the standard sanctions, rather than new engine machinery.
  6. *The tool's config surface first*: where a flag has a config-file equivalent, the answer is a pinned value in the tool's config and no script change at all. Rules that out case by case before any of the above is built.

  Rejected on sight: reading an unbounded env var inside every command — invisible in the manifest and enforcing nothing. Whichever route wins, the drift report should name what it preserved, so tolerance is visible rather than silent.

  Trigger: the first consumer needing an argument that the standard's own aggregate must also carry, for a reason that is not a fixable environment defect. The case that surfaced this — a PHP CLI with no ini file needing `--memory-limit` — is one the machine should fix, not the standard.
- **Composing several rule sets is silent about overlapping blocks.** `SyncConfig::withRuleSet()` is additive and every set's rules fold together by resolved path, which is what lets a consumer declare a tier and a forge-specific companion side by side — the composition is documented in the [authoring guide](authoring-org-packages.md#several-standards-in-one-consumer).
  What it does not do is notice when two *separately declared* standards declare a same-label block: the later one replaces the earlier, and the earlier declaration's content is gone with nothing reported.
  Within one standard that is the documented override mechanism and one author sees both declarations; across two, neither author can see the other, which turns an override into action at a distance.
  Composer scripts left this entry on 2026-09-29: their declarations merge, so a standard declared beside another adds to what that one declares instead of replacing it.
  Direction: report cross-rule-set overlap in the plan the way drift is reported, which needs no semantic change and makes the accident visible.
  Trigger: the first pair of separately declared standards found to declare one label.
- **A strict composer script** — an optional `strict:` on `ComposerScript`, defaulting to `false`, so adding it is non-breaking.
  Strict means the script runs exactly the commands its declarations list together and the project's own commands are removed — the behaviour before 2026-09-29, with other standards' contributions still merged in.
  If any declaration of a script is strict, the merged script is; it needs no lock, since anything undeclared is removed anyway.
  Trigger: a standard needing a script guaranteed to run nothing it did not declare, such as a release or deploy entry point.
- **An entry that must be absent** — what a child standard needs to drop a step its parent declares: enforce-absence at entry level, the mirror of a contribution.
  Since 2026-09-29 a same-name redeclaration of a composer script adds rather than replaces, so it can no longer serve as the override that removes a parent's step, and a strict script would not provide it either, since a strict list still keeps every declaration's commands.
  Trigger: a second-tier standard that needs to drop a parent's step.
- **Union returns for same-label blocks** (a `GitignoreRule` opting in) — the default stays last-wins; union arrives as chosen construction behaviour with a pre-fold coalesce step, and the pre-fold merge that `ContributesToList` introduced is that step.
- **A generic `ImportRule` convenience** over the per-tool classes — trigger: the tail of tools grows long; never first.
- **The per-root rule-factory seam** — trigger: the first real consumer with sync roots below the project top (a central-vendor monorepo).
- **`ManagedBlock` per-candidate syntax** (adopting `AppliesAtPath`) and an abstain-when-absent construction flag — trigger: a real same-format case needing either.
- **Enclosed-comment marker support** (`<!-- -->`) — expected trigger: managed README sections; that adds a comment tail to the marker grammar.
- **A configurable distributed directory** — `Package` hardcodes `templates/`, which is what makes a rule structurally unable to point at the package's own config. Making it a constructor parameter is additive (an optional third argument), so deferring costs nothing later. Trigger: a real org package needing a different directory name, or one wanting to distribute from its repository root. Neither known case needs it — variants of a file separate by subdirectory under `templates/` today, and content a tool fetches for itself is not distributed by the engine at all.
- **Catalog generation for org packages** — `RuleCatalog`'s project shape becomes a parameter so an org can generate docs for its own rules; the same work makes the catalog's refusal guards testable. Trigger: an org package wanting generated docs, or the next change to the guards.
- **The phpunit dev pin lifts back to `^13`** when psalm's `sebastian/diff` cap moves.
