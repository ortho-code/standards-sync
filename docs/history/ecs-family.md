# The ECS family — decision record

Part of the [rule-model design record](rule-model.md), split out per family; the contract, the doctrine, the cross-family decisions, and the roadmap live there. Entries are chronological under their original headings.

## Decided 2026-08-02 (R3, third tool) — the ECS family

The third tool family, chosen because `ecs.php` shares Rector's fluent-builder config style (same Symplify heritage) — the first real cross-family reuse test of `Formats/Php/FluentChainWriter`. Designed against the verified config surface of ECS 13.2.17 (read from the installed source, not recall):

- Config discovery: `--config`/`-c`, else `ecs.php` in the working directory — a single candidate, no `.dist` variants (`EasyCodingStandardContainerFactory`), shared as `EcsConfigFile::target()`.
- The config file must return a callable receiving `ECSConfig`; `ECSConfig::configure()` returns `ECSConfigBuilder`, which implements `__invoke(ECSConfig)` — the documented canon, structurally identical to Rector's builder. The older closure form (`return static function (ECSConfig $ecsConfig): void {…}`) is **actively deprecated**: a closure root config prints a console warning and sleeps five seconds on every run, so the fluent-only scope needs less justification here than it did for Rector.
- `->withSets([...])` takes file-path strings — the native Tier A import, under the same method name as Rector's: each set file is `require`d, asserted callable, and invoked against the same `ECSConfig`; the official `SetList` constants are `__DIR__`-based path constants. The deprecation guard covers root configs only, so set files may stay closures (ECS's own sets are).
- An in-the-wild sharing variant to know about: a monorepo hosts a base-ruleset file that returns the *builder itself*, and each package's `ecs.php` does `$config = include '…/base-ruleset.php'; return $config->withPaths(…)->withSkip(…);` — a valid fluent chain that never contains the text `ECSConfig::configure()`.

The decisions:

- **Fluent-only scope, marker-guarded.** `EcsConfigFile::assertFluentChain()` requires the literal `ECSConfig::configure()`; anything else — the closure form, the include-chain variant above — is refused at plan time with a convert-to-fluent message (the Rector / inline-`includes:` precedent). Rejected: guarding only the edit's mechanics (the file ends in a `;`-terminated chain), which would edit include-chain configs too. That is the same textual edit under a weaker precondition, editing blind on top of a base the rule cannot see: the appended org set would double-load a standard the include already carries, and the failure mode moves from a loud one-time refusal to a silently wrong config that syncs green. The cost asymmetry decides it — a false refusal costs one manual conversion; a wrong edit is silent misconfiguration. Revisit against real include-chain repos when one adopts the engine.
- **`EcsBaseSet`** (param `set:`, the set file's consumer-root-relative path — the 2026-08-02 param revision under [the Rector family](rector-family.md), applied to both rules) mirrors `RectorBaseSet`'s behaviour table: an absent file is created as the canonical fluent skeleton holding just the import, deliberately without `withPaths()` (the maintainer owns their parameters); a chain without `withSets` gains the call appended at the end; a block-form array gains the rendered entry (`__DIR__ . '/<path>'`), matched verbatim with no quote-stripping; an inline single-line array is refused with a convert-to-block-form message. Implements `ExplainsDrift`. Shared family knowledge lives in `EcsConfigFile` (target, fluent guard, created skeleton), mirroring `RectorConfigFile`. Side fact: create-on-absent also means a consumer never meets ECS's own interactive config generator (ECS offers to write an `ecs.php` when none exists).
- **`FluentChainWriter` is reused unchanged** — the cross-family reuse this phase was chosen to test holds at design level; no new `Formats/` code. Verified: the `->withSets(` call matcher cannot false-hit `->withPreparedSets(` or `->withPhpCsFixerSets(`.
- **Ship the base set only** — the Rector review's parking discipline applied a priori; the floor and pin surfaces are recorded here for when a real need appears:
  - Levels: four additive methods (`withSpacesLevel`, `withArrayLevel`, `withControlStructuresLevel`, `withDocblockLevel`), a natural int over a fixed per-category rule list; overshooting the list is **silently clamped** to its end (Rector warns instead). The extra hazard a future floor must handle: ECS itself refuses a level method combined with the equivalent prepared set (or `common`) with a `SuperfluousConfigurationException` — a blindly written floor can make the consumer's own ECS run throw.
  - Pin-relevant builder semantics: `withSets` merges across calls, while `withRules` and `withSkip` overwrite the builder's earlier state.
- **Per-tool classes stay** — the R2 doctrine's "never first" applies to its second member too: `EcsBaseSet` is written as its own small rule over the shared writer. Agreed rider: the build report breaks down what is byte-identical versus tool-shaped across `RectorBaseSet`/`EcsBaseSet`, so any extraction is proposed on evidence; the trigger remains a third fluent-builder tool.
- **Naming**: `Rules/Ecs/` with `EcsConfigFile` and `EcsBaseSet` — the tool prefix PascalCase-normalized per the `PhpStan` precedent (the tool spells itself "ECS"); the constructor param is `set:`, ECS's own `withSets` vocabulary. Config-flavoured rule names were reconsidered and rejected (2026-08-02): `EcsConfig` collides with the tool's own class — PHP resolves class names case-insensitively, so `EcsConfig` and `ECSConfig` are the same name to an importer — and `EcsConfigFile`-style names describe the edit target (and the existing support class) rather than the declared artifact; the artifact-noun convention stands.

### Agreed 2026-08-03 — the rider's answer: byte-identical shells, per-tool held; the shared rendering moves to `Formats/`

The build-report rider above (byte-identical versus tool-shaped across `RectorBaseSet`/`EcsBaseSet`) was never recorded; measured now:

- **The rule classes are near-clones.** They differ in exactly the class name, which `*ConfigFile` they delegate to, and the tool's name in three message strings. The `METHOD` constant (both literally `'withSets'`), the constructor validation, the `apply()` shape (create-on-null → assert fluent → ensure entry), and the `entry()`/`setsCall()` rendering are byte-identical — roughly 85% of each class.
- **The `*ConfigFile` support classes are the genuinely tool-shaped part**: candidate lists, the fluent marker, the created skeleton's use/return lines.
- **Per-tool classes stay** — the extraction trigger (a third fluent-builder tool) is receding, not approaching: the next two families are XML (psalm) and YAML (deptrac). The dual-maintenance cost is real but bounded at two (it bit once — the `set:`-param revision touched both rules in one change); an abstract base is a same-day decision if a third fluent tool ever lands, on the evidence above.
- **The consequence, agreed as the next phase (before psalm) — the fluent-family cleanup.** No recorded decision changes; this *applies* the `Formats/` doctrine (editing mechanics are facts about the format, serving multiple families — two are served):
  1. `FluentChainWriter` gains the two renderings the rules duplicate — the `__DIR__`-anchored entry (with the expression-text refusal *inside*, beside the rendering it protects: a quote in the path breaks the rendered entry's quoting) and the multiline array-call rendering. Both base-set rules shrink to what is genuinely theirs: target delegation, the apply skeleton, tool-named messages. Validation stays construction-time.
  2. `Path` gains a relative-only named constructor (`from<Source>` conventions; exact name at build): the relative-only invariant is currently restated four times (`FileTarget`, twice in `Package`, the base-set rules) and the value-object doctrine puts a repeated invariant on the type. All call sites adopt it.
  3. `PhpStanIncludedRuleset` aligns on the same validation — today it accepts anything non-empty; afterwards all three import rules tell one validation story. The one observable tightening: a hand-written absolute ruleset path newly refuses at config-build, loudly.
  4. Acceptance: behaviour-preserving except that tightening — the scenario suite must pass with no fixture change.
- Also settled, from the same review: the expression-text and absolute-path constructor checks are **not** vestiges of the pre-`Package` era — `Package::path()` cannot produce bad input, but the constructors remain public API for hand-written paths (consumer overrides, fixtures, custom rule sets), where the checks turn a silently broken consumer config into a loud config-build error. Checks on value-shaped params keep living in their value objects (`Label`, `PhpStanLevel`, `PinnedValues`, `FileTarget`) — that existing pattern *is* the house answer to "generic helpers for constructor checks".
- **Built the same date.** `Path::fromRelativeString()` (adopted by `FileTarget`, both `Package` sites, both base-set rules, `PhpStanIncludedRuleset`); the `__DIR__`-anchored entry as `Formats/Php/DirAnchoredEntry`, a value object validating at construction (expression-text refusal beside the rendering it protects) — each base-set rule holds one `DirAnchoredEntry` and nothing path-shaped besides it; `FluentChainWriter::createArrayCall()` for the created-config call. The relative-only message is one generic text in `Path` naming the offending value — the site-specific phrasings were dropped deliberately (maintainer's call): the exceptions convention builds the message where the condition is detected, and that is now the value object. Scenario suite passed with zero fixture changes; the one tightening landed as planned.
- **Refined the same date, from post-build review.** First build had the entry rendering as a writer static (`createDirAnchoredEntry()`), diluting the writer's edit-only cohesion and leaving the rules holding derived state (`Path` + rendered string); the value object fixed both — it *is* the recorded house pattern (checks on value-shaped params live in their value objects). Also single-sourced the block-form array-call shape inside the writer: one private line-renderer, two placement policies (created config carries the canonical unit; append follows the file's own indentation) — previously two look-alike renderings sat side by side. Both behaviour-preserving, zero fixture changes.

### Found 2026-08-11 — the include-chain revisit trigger has fired; root-anchoring turns out to be a precondition, not a detail

The fluent-only scope above parked its refusal of the include-chain variant behind a condition: "Revisit against real include-chain repos when one adopts the engine." One has now been measured — a monorepo of exactly the anticipated shape, its shared base hosted as a script under a tools directory, with eleven configs chaining over it (one CI entry point plus ten package configs). Measured by running `EcsBaseSet` against the real files rather than reading them, which is what surfaced the second finding:

- **The refusal fires as designed, at a scale the cost model did not anticipate.** All eleven configs refuse; none contains the literal `ECSConfig::configure()`. The cost asymmetry that decided the guard is unchanged and still sound — a false refusal is loud and one-time, a wrong edit is silent — but "one manual conversion" was the wrong unit. The adopter's choice is between converting eleven files (discarding a shared base they deliberately invested in) and the engine learning the pattern.
- **New precondition: `DirAnchoredEntry` assumes the target sits at the consumer root.** Its rendering is `__DIR__ . '/<consumer-root-relative path>'`, which is only correct because `EcsConfigFile`'s single candidate is a root-level `ecs.php`. For a config at `<root>/a/b/`, `__DIR__` is `<root>/a/b`, so the entry resolves to `<root>/a/b/vendor/…` — and because ECS `require`s each set file, the result is a load failure, not a silent no-op. The edit reads as clean and produces a config that cannot run. So making the target configurable would not be sufficient on its own: the anchoring must become relative to the target's own directory, and `DirAnchoredEntry` currently holds only a root-relative `Path`. `RectorBaseSet` shares the value object, so the change touches both fluent families. Not a defect today — nothing can point a rule below the root — but it gates any option that edits a non-root config.
- **Create-on-absent is a second door to silent misconfiguration, for `--config`-driven repos.** A repo that invokes ECS with an explicit `--config` has no root `ecs.php`, so the create-on-absent branch writes one that no runner ever loads: `sync` succeeds, `--check` stays green, the standard is enforced nowhere. That is the outcome the fluent-only guard exists to prevent, arriving from the other side — absence read as "greenfield" when it means "configured elsewhere". `withoutRule()` is the existing opt-out, but it only helps someone who already knows to reach for it.
- **Two confirmations, no change needed.** The `->withSets(` matcher's inability to false-hit `->withPhpCsFixerSets(` was verified at design time against constructed input; it now holds against a real config where both calls coexist *and the `withPhpCsFixerSets` call appears first*. Separately, a set file may return the builder rather than a closure: `ECSConfigBuilder` implements `__invoke(ECSConfig)`, which satisfies the require-plus-callable contract, so the allowance recorded for closures covers builders too.
- **Cross-family coupling worth stating for org authors.** A consumer config calling `->withEditorConfig()` derives indentation, line endings and final-newline from `.editorconfig`. Where an org package also ships a managed `.editorconfig` block, that block changes what ECS *enforces*, not merely what editors do — an `indent_style` disagreement between a copied block and the consumer's existing style reformats the codebase on the next fix run. Authoring a block per org rather than reusing another's is the mitigation.
- **Nothing is decided.** Three shapes are on the table for the guard, recorded so the next pass starts from them rather than rediscovering them: (a) teach `EcsConfigFile` to follow the include, which removes the stated justification for refusing by letting the rule see the base it edits over; (b) narrow the guard to admit a chain over an included builder *when that base is itself an engine target*, making the shared base the managed file and leaving the dependent configs untouched; (c) hold the refusal and require conversion to self-contained fluent chains. (b) asks least of an adopter and preserves the shared base, but it is a change to a dated decision and is not agreed. (a) and (b) both depend on the anchoring precondition above. Whichever lands is a pipeline behaviour change and needs its scenario fixtures — an include-chain config and a below-root target are both new shapes for the catalog.
