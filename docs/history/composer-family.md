# The composer.json family — decision record

Part of the [rule-model design record](rule-model.md), split out per family; the contract, the doctrine, the cross-family decisions, and the roadmap live there. Entries are chronological under their original headings.

## Designed 2026-08-11 (R3, fifth tool) — the composer.json family: the first JSON tool, and the first target another program writes

Promoted to the next family on 2026-08-05 as the engine half of the tool-enforcement flag (see the roadmap in [rule-model.md](rule-model.md)): synced configs do not make a repo install or run the tools, so the four shipped families are enforceable on paper only. It scores on leverage and on R3 coverage at once — the first JSON tool (no comments, so the marker family is out by construction), the first target with a competing automated writer (composer itself), and the first with constraint-value semantics.

**Verified facts (composer 2.10.1 on PHP 8.5.7, read from the distributed source and probed live — never from recall):**

- **Composer edits the manifest the way this engine does.** `Composer\Json\JsonManipulator` is regex-driven targeted splicing over the raw text, with detected indentation and line ending — no parse, no reserialization. Probed: `composer require --dev` on a two-space manifest preserved the indentation, the key order, and a hand-written `scripts` block. The two writers can co-manage the file.
- **The one block composer re-renders is a requirement section under `config.sort-packages`**: `addLink()` re-renders the whole object through composer's own sort (platform packages first, then `strnatcmp`). An appended entry survives; composer tidies its position on the consumer's next `require`.
- **Lock staleness is key-scoped.** `Locker::getContentHash()` hashes only `name`, `version`, `require`, `require-dev`, `conflict`, `replace`, `provide`, `minimum-stability`, `prefer-stable`, `repositories` and `extra`, plus `config.platform`. Writing `scripts`, or any `config` key but `platform`, leaves the lock valid; writing a requirement does not.
- **What a stale lock costs**, probed by exit code: a requirement absent from the lock, or present but not satisfying the written constraint, fails `composer install` with exit 4 — `ERROR_LOCK_FILE_INVALID`, raised by `Installer::doInstall()` on a missing root requirement, not on a hash mismatch alone; a constraint the locked version still satisfies warns and exits 0; a `scripts` write is silent and exits 0. `composer validate` exits 2 on any hash mismatch, and 0 under `--no-check-lock`.
- **One target candidate**, `composer.json`, with no `.dist` convention — the dist resolution policy is inert here. The only override is the `COMPOSER` environment variable (`Factory::getComposerFile()`), an environment fact rather than a file variant.
- **JSON has no comments**, so the enforced-comment feature is inapplicable, as it is for XML.
- **Requirement values are flat strings** (the schema's `additionalProperties: {"type": "string"}`); `scripts` values are `array|string` over an open key set, and composer resolves `@name` references between scripts (`EventDispatcher::isComposerScript`), which is a project's native way to wrap an owned script in its own.
- **A package in both requirement sections is a warning at validation and an intersection at resolution.** `composer validate` exits 0 saying it "can lead to unexpected behavior", and composer's own validator names the overlap `$requireOverrides` — but neither entry overrides the other: probed, both constraints apply at once, so `require: ^3.0` beside `require-dev: ^1.0` makes the project unresolvable ("found psr/log[1.1.4] but it does not match the constraint"), while a compatible pair resolves and locks into the runtime `packages` section. The duplicate is a state no maintainer writes deliberately, and it can make a repo uninstallable.
- **Constraint comparison belongs to `composer/semver`** (`Intervals::isSubsetOf`; `php` is its only requirement). Against a declared `^2.5`: `^2.5.7`, `~2.5`, `2.5.7`, `^2.5@dev`, `>=2.5 <3.0`, `2.5.*` and `3.x-dev` satisfy a `>= 2.5` floor; `^2.0`, `*`, `dev-main`, `dev-feature/x` and `^2.5 || dev-main` do not; `^3.0`, `>=2.5` and `^2.5 || ^3.0` satisfy that floor while *not* being subsets of `^2.5` itself — the pair of results the floor semantics below turns on.
- **`Intervals::get()` separates numeric ranges from branch names**, which is what makes "has no lowest version" decidable rather than guessed: `dev-main` yields zero numeric intervals, while `*` yields one starting at `0.0.0.0-dev`. Unparseable text (`''`, `abc`) throws `UnexpectedValueException`.
- **No position-aware JSON editing exists in PHP.** `seld/jsonlint` — composer's own parser — tracks offsets in its lexer but exposes only decoded values; `json_decode` plus `JSON_PRETTY_PRINT` rewrites every line of a two-space manifest. Composer hand-rolls its own manipulator: the format's primary consumer confirming the gap, as psalm did for XML.

**The decisions:**

- **Three members, two of them first.** `ComposerRequirement` and `ComposerScript` shipped first; `ComposerConfigSetting` followed in its own phase (built 2026-08-11). Object-valued settings (`allow-plugins`) need union-or-replace semantics of their own and wait for a real need.
- **`ComposerConfigSetting` pins rather than floors.** Composer's config values have no ordering to floor, so the declared value is enforced outright — what a project may legitimately choose does not belong in the standard at all. Its setting name takes composer's own dotted spelling (`preferred-install.dist`), the syntax `composer config` itself uses, which means the signature never has to widen the first time an org needs a setting nested under another. It reads nothing: the writer's decoded-equality early return leaves a matching value byte-identical, so one write serves adding, correcting and leaving alike. Writing it required widening `JsonObjectWriter::write()` from `string` to `string|bool|int` — `sort-packages` is a boolean, and a string-only writer would have written the *text* `"true"`; a widening parameter is breaking for implementors, which is free here only because the writer sits behind the deptrac-enforced `Formats/` seam. Recorded rather than built: `config` sits outside the lock's content hash **except `config.platform`**, so this member is lock-free for every setting but that one; a per-key `ExplainsDrift` branch for a single composer key was judged not worth it.
- **`composer/semver` is required, and the family stays in this package.** [distribution.md](../distribution.md)'s split trigger — a family needing the tool's own code moves to its own package — is read by its purpose: it protects a consumer from carrying a dependency for a tool they do not use, and every consumer of this engine installed it *with* composer. The reading is therefore amended for composer specifically, one package stands, and the cost is a single library whose only requirement is `php`. Rejected: hand-rolling constraint comparison (semver parsing is precisely the framework weight the prior attempt died of); a `standards-sync-composer` split for a tool no consumer can avoid; and `composer/composer` as a JSON backend — see the writer decision below.
- **`Rules` gains one scoped vendor grant, not a general one.** A `ComposerRules` deptrac layer over `src/Rules/Composer` is allowed `Core`, `Formats` and `Vendor`; the general `Rules` layer excludes that directory and stays provably vendor-free. Rejected: an interface in `Core` with a semver-backed implementation in a vendor-allowed layer — rules are pure values constructed by the org package, not services wired at a composition root, so such an interface has no injection point (the org would have to name the implementation at every declaration site) and nowhere to live that both sides can see without putting a composer-shaped concept inside the pure pipeline. Trigger to revisit: a second vendor-backed value grammar — npm's semver, for a `package.json` family — at which point a shared vendor-allowed value layer has two residents and earns its directory. The `Rules` layer's redundant `classNameRegex` collector goes in the same change: it matched the identical set as the directory collector, and `--fail-on-uncovered` already catches a class that falls out of every layer.
- **The floor is the lower bound, not the subset.** A consumer's constraint satisfies the org's when nothing it allows can resolve below the org's lowest version, so a project may move ahead to a newer major and only a constraint reaching *below* the floor is rewritten. Rejected: subset semantics, under which `^2.5 || ^3.0` drifts and is pulled *back* to `^2.5` — the copy behaviour "floors, not copies" exists to refuse; presence-only, which drops the tool version out of the standard entirely; and pinning the org's text verbatim, which downgrades a consumer's stricter pin.
- **A failing constraint is repaired alternative-wise, never reset wholesale.** The constraint is split on `||` (composer accepts `|` too, and a multi-part alternative like `>=1.0 <2.0` stays one unit); only the alternatives reaching below the floor are replaced by the org's constraint, the rest are kept verbatim, and the result is deduplicated and rejoined. So `^1.0 || ^3.0` becomes `^2.5 || ^3.0`, `>=1.0 <2.0 || ^3.0` becomes `^2.5 || ^3.0`, and `^1.0 || ^2.0`, `^1.0`, `*` and `dev-main` all become `^2.5`. **The property this buys: the rewrite never removes a version that already met the org standard**, so it can only break an install that was already below it. A constraint that already meets the minimum is returned exactly as written — separator spelling included, so `^2.5|^3.0` is not normalized to `^2.5 || ^3.0` — because normalizing is only ever collateral of a raise, never a reason for one. Two consequences of repairing per alternative, pinned by fixtures: the replacement lands where the failing alternative was written, so `^3.0 || ^1.0` becomes `^3.0 || ^2.5` rather than being reordered; and a branch alternative meets no minimum, so it is always replaced — which means it vanishes outright when the replacement duplicates an alternative already kept (`^2.5 || dev-main` becomes `^2.5`). A project that genuinely tracks a branch uses `withoutRule()`, the standing opt-out. A wholesale reset was the first design and is rejected as a defect, not a preference — writing `^2.5` over `^1.0 || ^3.0` leaves a project whose lock holds 3.2.1 with a manifest its own lock no longer satisfies, which is `composer install` exit 4 on a repo that was already compliant. Considered and unreachable: deriving the replacement from `composer.lock`, which is the only true source for what a project actually runs — a rule receives one file's content and never touches the filesystem, so a second file has no seam; the honest path is the parked per-root rule-factory seam, and this family is the wrong reason to unpark it. Residual, accepted: a project locked *below* the floor still gets a failing `composer install` until it updates, which is the standard doing its job.
- **A branch constraint satisfies no floor and is rewritten.** `dev-main` can resolve to any version, so it is drift, and the explanation says exactly that — the reviewed diff carries its own justification. Rejected: leaving it with a note, which is the silence the enforce-over-silence doctrine exists to prevent; `withoutRule()` remains the opt-out for a package a project genuinely co-develops. An org constraint that itself names only a branch is an authoring error and is refused at rule construction; an unparseable constraint on either side refuses at plan time, naming the file, the package and the value. *(The construction refusal was removed 2026-08-29 — such a constraint is now pinned; see the entry at the end of this file.)*
- **The requirement type is declared, and satisfaction is directional.** One rule covers both sections: `ComposerRequirement` takes `type:` — composer's own word for it (`JsonManipulator::addLink(string $type, …)`, `Link::TYPE_REQUIRE`) — as a `RequirementType` enum whose cases `Runtime` and `Development` are backed by composer's section names, defaulting to `Development` as the dominant case. A development requirement found in `require` is satisfied, because a runtime requirement is the stricter placement; a runtime requirement found in `require-dev` is *not*, because the package would not be installed in production. Requirement link types are a genuinely fixed, tiny set, so this is the closed-set case an enum is for rather than the open tool surface the conventions warn off. Rejected: separate `ComposerDevRequirement` / `ComposerRequirement` classes — the runtime case is concrete and near (`php` as an org-wide minimum), and one artifact split across two classes is the shape to avoid, not the one to plan for.
- **One invariant covers placement, moving and duplicates: the package is required exactly once, in a section that satisfies the declared type, at or above the floor.** Every case falls out of that sentence — declared runtime but found only in `require-dev`, it moves; found in both sections, the `require-dev` entry goes whichever type is declared; declared development but found in `require`, it stays; found nowhere, it is inserted into the declared section. Removing a key is an ordinary content transform — enforce-absence is the mirror of enforce-presence, recorded pre-R0 and unrelated to the refused *file* deletion — so a move is a removal plus a write: two idempotent operations composing into one legible two-line diff, with the next run finding it in place and no-oping. A constraint that already satisfies the floor is carried across a move unchanged, so a move never downgrades a deliberate pin. Moves only ever tighten: the rule can promote a requirement to production but never demote one. Removing the duplicate is not tidying — because both entries' constraints apply at once, the removed one is a hidden extra constraint that can make a repo uninstallable. Two consequences stated rather than out-clevered: the surviving entry keeps its own constraint (floored), so dropping a stricter dev duplicate loosens the effective constraint down to the floor, and "stricter" between two arbitrary constraints is not well-ordered anyway; and merging the pair into one computed constraint is the interval-rendering cleverness rejected under the repair decision above. Rejected: adding the entry to the declared section and leaving the old one, which writes a manifest saying two contradictory things and leans on composer's own warning to explain it; and refusing at plan time, which aborts an entire sync over a state the engine can correct safely. This makes `ComposerRequirement` the first shipped rule that removes content a consumer wrote — recorded deliberately, because that is a first.
- **The family abstains when the manifest is absent, and the abstention is reported.** A root with no `composer.json` is not a composer project: there is no tool default to be blind to, so the enforce-over-silence premise does not apply, and creating a nameless package in that directory would be picked up as real by composer and by tooling. This is the symmetric null's first shipped user. **The note is right because a root is a project**: the install-location decision established that each sync root is its own consumer project, so every root has a manifest and a root without one is anomalous — exactly the case worth telling. It is *not* justified as a leg for roots below the project top; that is the monorepo shape the per-root factory seam is parked for, and in that world most roots legitimately have no manifest of their own, so this note would fire on each of them on every run forever and train readers to ignore notes — including the shadowing note, which is actionable. Whoever unparks that seam revisits this note with it. The manifest is also the one config in these families that a consumer cannot lack in practice — this engine is installed with composer, so a project root always has one — which is what keeps abstention from being a hole. Rejected: a per-rule `onMissing:` knob, which is the seam the phpstan family shipped and then removed outright, and which puts a create-or-skip choice on every rule when what varies is one org-level question. Recorded as the mechanism should an org ever want manifest-less roots bootstrapped anyway, deliberately not built: a `ComposerBaseManifest` seeded from an org template, declared before the other composer rules — the `PsalmBaseConfig` pattern, where the template bootstraps and the rules converge — which needs no engine change, because the fold already lets the first rule to meet an absent file decide the created base.
- **`ComposerScript` owns its named script.** The declared command list is written verbatim and a deviating or missing script is rewritten, so an org gets a known entry point CI can call by name. A project needing extra steps declares its own script and calls the owned one through composer's `@name` reference — the tool's native escape hatch, so no union semantics are needed. A string-valued script is replaced by the list form. Union semantics ("ensure this command is present, leave the others") stay available as a later named constructor on the same rule, so both readings remain explicit at the declaration site.
- **Entries are appended; composer's sort is not replicated.** Where to insert is composer's own algorithm, declared in the very file being edited, and reproducing it is the rediscovery smell — with the cost of not doing so being one reordered block in some future `composer require` diff. An org that cares enforces `config.sort-packages` and lets composer tidy the block itself, which is what the deferred third member is for.
- **Lock staleness rides `ExplainsDrift`.** The requirement rule's explanation names the follow-up (`composer update <package>`) at the moment it matters, on drift. No plan-level machinery: the fact is one sentence, and the sentence belongs to the rule that caused it. Recorded alongside: `ComposerScript` causes no staleness at all, because `scripts` sits outside the lock's content hash.
- **`Formats/Json/JsonObjectWriter` is hand-rolled**, consistent with the neon, PHP and XML members. The re-assessment every new `Formats/` member owes (see [conventions.md](../conventions.md)) was run with the dependency-weight objection explicitly withdrawn, so the judgement is capability and fit alone. `JsonManipulator` would cover all three members and is bug-for-bug what `composer require` runs, but it offers no read operation, signals failure by returning `false` rather than throwing, and speaks composer's vocabulary (`addLink`, `addRepository`, `addConfigSetting`) — which a general JSON layer would then have to re-derive genericity out of, and which would put a vendor edge on `Formats`. Against that, JSON is the least dangerous format hand-rolled here: the corruption class that bit the neon writers was comment boundaries inside quoted values, and JSON has no comments. Rejected outright: `json_decode` plus re-encoding, which rewrites every line of a two-space manifest — the recorded reserialization anti-goal. Re-assess when a second JSON family (renovate, `package.json`) arrives.
- **The writer preserves layout it did not create, and creates in the canonical shape.** An object the project wrote on one line keeps that line when a member is added — including the member's own value, so a list joining a one-line object renders on that line too — while an object the writer creates or fills is written one member per line. Composer itself is no guide here: probed, writing into `"config": {"sort-packages": true}` leaves it neither compact nor expanded but split mid-object, an artifact of its regex approach. Rejected: expanding a one-line object on write, which is the more canonical shape but relayouts bytes the project wrote for a member it did not ask about. Known limit, recorded rather than fixed: the indentation unit is read from the file's first indented member — composer's own heuristic, correct for any real manifest, wrong for a file whose first member is itself nested. Rejected: splitting reading into a `JsonObjectReader` — the member scan *is* the class and all three operations need it, so a split needs a third class to hold it, and reading exists in service of writing (deciding drift, and leaving an equal value byte-identical). The layer's other members are writers that read too. Trigger to revisit, with the layer-wide naming question that rides along: a genuine read-only consumer, a rule that inspects a file it never writes.

**Build scope:**

1. `Formats/Json/JsonObjectWriter` (`read`, `write`, `writeList`, `remove` over one internal span locator) and `Testing/Validation/JsonValidator`, unguarded because `json_decode` is core. The document is validated once up front so the scan may assume valid JSON and every refusal names a real problem; the scan is string-aware, so a brace, comma or colon inside a value never counts; keys are compared decoded, so a manifest carrying composer's escaped `vendor\/package` spelling matches and is not duplicated; values render with `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE`, composer's own style; insertion follows the object's last member, copying its indentation, with the file's detected indent (four spaces as the fallback, composer's default) for created objects; line breaks follow `Core/Text/Lines`, this engine's LF convention, rather than composer's CRLF detection. Loud refusals: a root that is not an object, a path segment whose existing value is not an object, and a duplicate key at one level.
2. `Rules/Composer/`: `ComposerManifest` (the target and the scripts section name), `Requirement/` (`ComposerRequirement`, `RequirementType`, `VersionConstraint`), `Script/ComposerScript`; the deptrac grant; the `composer/semver` requirement. Scenario fixtures per the behaviour-catalog rule: added to an existing `require-dev`; the section created; a satisfying constraint left byte-identical; a constraint below the floor raised; a branch constraint raised; an unbounded `*` raised; a requirement enforced where it already lives in `require`; a runtime requirement moved out of `require-dev`; a move carrying a stricter constraint across; a duplicate across both sections reduced to one; a wider constraint repaired alternative-wise (`^1.0 || ^3.0` → `^2.5 || ^3.0`) and a fully-below-floor one collapsing to the org's; an escaped package key matched rather than duplicated; tab- and four-space-indented manifests; a script created, rewritten, left alone, and replacing a string form; a family fixture folding both rules; and an absent manifest creating nothing. `VersionConstraint` unit cases carry the whole verified table above plus the unparseable refusals.
3. The abstention carrier and its report line: `Core/Plan/Abstention` (the resolved path and the rules that had no opinion), carried on `Plan` beside the changes, rendered through the report's existing `notes()` seam as the second note kind — the trigger that entry parked against, now arrived. The engine already builds the applications it currently discards when a file's rules all abstain. The note is generic rather than rule-authored, because under enforce-over-silence every abstention should be told, not only the ones whose author opted in; it renders on every run, in-sync included, and leaves the `--check` exit code untouched.
4. Org wiring closes the family. **The flag's third artifact lands here too** — an org-authored CI managed block running the tools and `sync --check`. Without it this family guarantees the tools are *installed* and nothing ever runs them, so the enforcement story is only real once all three exist; it needs no engine work (`ManagedBlock` in a YAML CI config) and is therefore org authoring, not a fifth phase.
**Built 2026-08-11**, in the four steps above. What the build added or changed beyond the design:

- **`Formats/Json/JsonObjectWriter`** with `JsonMember` and `JsonObject` beside it — the span structures became small value objects rather than the documented array shapes its `Formats/` siblings use, because the array keys were the noise the scanner read worst; `XmlElementWriter` follows in the sweep below. The writer preserves a one-line object's layout on insert and renders a list inline there too; a rejected first attempt expanded such objects to one member per line, which relayouts bytes the project wrote.
- **`ComposerRequirement::apply()` has no compliant branch.** Raising a constraint that already meets the minimum returns it unchanged and writing an equal value leaves the file byte-identical, so adding, raising, moving and leaving all fall out of one write — the `PsalmLoosestErrorLevel` shape. Two defects the build's self-review caught: `explain()` reported a duplicate as a below-minimum constraint (a false statement about a compliant value), and the recorded refusal for an unparseable constraint named only the value, not the package and section.
- **`raisedTo()` returns the constraint verbatim when it already meets the minimum**, separator spelling included — an earlier version rejoined unconditionally and rewrote a compliant `^2.5|^3.0` into `^2.5 || ^3.0` purely to normalize it.
- **The abstention note**, per the third step: `Core/Plan/Abstention`, `Plan::abstentions()`, and the report's second note kind. `Engine::foldFile()` returns `Change|Abstention`, keeping the applications it previously built and discarded.
- **Consumer wiring.** The flag's three artifacts land together — the tool requirements, a check script running them, and a managed workflow calling that script by name; an org should pin the workflow against its declared script name in its own suite, so a rename cannot leave CI running nothing. Verified live in the test consumers, including the verified tool fact the flag predicted: `composer install` merely warns (exit 0) about a stale lock when the newly required package is already locked transitively, and **exits 4** naming the package when it is absent from the lock — the loud failure observed rather than assumed.

5. Four sweeps held until this family is committed, so its diff stays about the family: `XmlElementWriter` moving from documented array shapes onto the `JsonMember` / `JsonObject` pattern this family introduced; `NeonValidator` and `XmlValidator` gaining the named extension constant `JsonValidator` carries; the remaining test files adopting the indented heredoc layout; and the remaining `expectExceptionMessage()` calls becoming `expectExceptionMessageIsOrContains()`, which PHPUnit 13 deprecates it in favour of and which it is a pure alias for.

## Changed 2026-08-29 — a declared branch constraint is pinned instead of refused

The 2026-08-11 entry above closes with "an org constraint that itself names only a branch is an authoring error and is refused at rule construction". That refusal is removed, and this entry supersedes that clause.

**Why the refusal had to go.** A package publishing nothing but branches could not be declared by a standard at all — `roave/security-advisories` is the real case, and it publishes only `dev-master` and `dev-latest`. The refusal existed because such a requirement could enforce no minimum and would therefore sit in a standard doing nothing silently.

**What it does instead: it pins.** A declared constraint with no lowest version is written outright, exactly as `ComposerConfigSetting` does for a config value. The reasoning is that entry's, unchanged and now applied a second time: where there is no ordering to floor, the declared value is enforced, because what a project may legitimately choose does not belong in the standard at all. It is also what the rule already did from the other side — a project's `dev-main` is rewritten when the standard declares `^2.5` — so tolerating a project's `dev-master` against a declared `dev-latest` would have been the asymmetry. The distinction is not cosmetic for the motivating case: `dev-latest` is the alias that resolves without loosening `minimum-stability`, `dev-master` is the branch, and a standard that names one while accepting the other says nothing useful.

Everything else the rule does — the wrong-section move, the both-sections duplicate, the abstention without a manifest — is unchanged, and the move now carries the pinned constraint rather than the project's. `description()` and `explain()` say which of the two a declaration is, so neither the catalog nor a drift line leaves it implicit.

**The mode is derived, not declared.** `VersionConstraint::lowestVersion()` already answers "is there a floor here", so the rule reads the answer off the constraint rather than taking a parameter that could contradict it.

*Rejected*: a sibling rule — one artifact (a requirement entry) split across two classes, with the section, duplicate and move logic duplicated or extracted for no other reason.
*Rejected*: an explicit enum beside the constraint (`MinimumVersion` / `PresenceOnly`) — built first, then dropped. It represents states the constraint already excludes, admits the contradictory pair (a numeric constraint declared as presence), and adds a parameter for a distinction the value carries by itself.
*Rejected, first*: leaving a project's own branch alone — presence rather than a pin. Considered and built before the pin, and wrong for the reasons above: it contradicts the config-setting doctrine and the rule's own treatment of a project-side branch.

**Accepted cost.** An author who means a floor and writes a branch now gets a pin silently where they used to get a loud refusal. That is the author's error to make, and the rule's own description states what it will do.

**The third mode, designed and not built: a null constraint meaning presence.** Requiring a package while stating no version at all is coherent and would slot in beside the two — but nothing needs it, and it has one unsolved detail: an absent package must be written with *some* constraint, and if the standard declines to name one the engine has to invent it, realistically `*`, which allows any major and cannot resolve a branch-only package under stable minimum-stability anyway. Making the parameter nullable later is additive rather than breaking, so contract-first does not force the decision now. Trigger: a standard that must require a package without stating any version.

**Fixtures added**, per the behaviour-catalog rule: a pinned branch adds the package it pins; a project on another branch is rewritten to it; a pinned requirement moves into the section that covers the need; and it drops the redundant duplicate the same way a floor requirement does. The unit cases that pinned the construction refusal are replaced by the pinned description, the byte-identical apply, and the rewrite explanation.

## Changed 2026-09-29 — declarations of one composer script merge

The 2026-08-11 entry's closing sentence, reserving union semantics for "a later named constructor on the same rule", is superseded.
The ownership itself stands for now: the declared commands, merged, are exactly what the script runs.

**Why.** A framework standard declared beside a tier needs one more step in the aggregate the tier declares.
With one declaration owning the script, it could only restate the tier's whole list, which differs per tier, so the framework standard would have had to exist once per tier; and whichever rule set came later replaced the other's list with nothing reported.

**What it does instead.** Declarations of one script merge before the fold, through the engine's `ContributesToList` seam (recorded in [rule-model.md](rule-model.md#decided-2026-09-28--contributions-to-one-list-merge-before-the-fold)): in declaration order, each adding its commands after the earlier ones', a command declared twice counting once.
The merged list is still exactly what the script runs, so a command a project added is still removed; keeping those needs the engine to remember what the standards declared, which is a later step.
**A same-name declaration therefore adds rather than replaces**, which retires the override the authoring guide documented for scripts.
No known standard relied on it.

**One form, no named constructor.** A `createExtension()` beside the owning constructor was in the design and dropped before the build, because the split decided only two merge details.
The owner's commands going first is what declaration order already does — the engine's general rule, and for the import-tier rules also the tool's own precedence.
A later owning declaration replacing an earlier one had no user; what it would serve, a child standard dropping a parent's step, is enforce-absence and is on the [roadmap](../roadmap.md) with its trigger.

**Rejected alternatives, in the order they were weighed.**
An order-dependent append rule beside the owning one — prototyped 2026-09-28 against the engine: declared after the tier it worked, declared before it the step vanished with `--check` green, and any unrelated drift in the manifest reported both rules as drifting although neither changed the outcome.
A slot script the tier references and the framework owns — it rests on the composer leniency below, so every consumer without the framework standard would print the missing-script line on every run, and a mistyped reference would skip a check the same way.

**Verified 2026-09-28 (composer 2.10.2):** a reference to a script that does not exist is not an error.
`"app-checks": ["@app-a", "@app-nope"]` runs `app-a`, prints `You made a reference to a non-existent script @app-nope` and exits 0, and an empty list behaves as a missing script.
So an aggregate calling a script nobody declares any more skips that check silently rather than failing.

**Fixtures**: one script scenario (a second declaration adds its commands after the first's, a shared one counting once) and two engine-level scenarios under `tests/Scenario/Engine/ListContributions/` (the order of two rule sets decides where each standard's commands go); no existing fixture changed.

## Changed 2026-09-29 — the project's commands stay, and commands the standards stop declaring are retracted

The 2026-08-11 decision "`ComposerScript` owns its named script" is superseded: the rule now declares commands a script runs rather than the script's whole content.

**Why.** Ownership removed every command a project added to a declared script, and the merged exact list of the previous entry still did, so a consumer could not add a step of its own to an aggregate at all.
Keeping those commands needed the lock ([rule-model.md](rule-model.md#decided-2026-09-28--a-lock-records-what-list-contributions-declared)), because without it a command the standards stop declaring would look exactly like one the project added and stay forever.

**What it does.** Each declared command is enforced present, and a missing one is inserted after the command declared before it, so a project that deleted `@app-sync-check` gets it back first.
Every other command in the script is the project's and stays where the project put it; only presence is enforced, so a project may reorder.
A command declared at the last sync and declared by nobody now is retracted, and it is recognised with arguments after it too, since a project's arguments do not make a command the standards stopped declaring the project's own.
A declared command always takes precedence over a retired one it extends, so a changed declaration never retracts its own replacement.
Without a lock nothing is retracted, which makes a deleted lock cost one sync's retractions and nothing else.
`explain()` names what is missing, what is retracted and which of the project's commands stay.

**Accepted cost, at adoption.** A project adopting a standard over a same-name script it already had keeps its old commands beside the declared ones: `["phpstan analyse", "php vendor/bin/phpstan --memory-limit=256M"]` runs the analyser twice until the project deletes its line.
That follows directly from never removing what a project wrote and retracting only what the lock records; the drift explanation names the commands that stay, and the diff shows them.
*Rejected*: taking the script over wholesale when no lock exists — a lock deleted later, or lost in a merge conflict, would wipe the project's additions the same way.

**Rejected alternatives.**
Tolerant ownership without memory, the owner enforcing a leading prefix and keeping the rest — it cannot retract, so a tier dropping `@app-phpcs` would leave it running in every consumer.
The merged exact list, which the previous entry built — order-independent and accurate in the report, but it removes what a project added, which was the requirement it failed.
A strict mode restoring it where a standard needs a script to run nothing it did not declare is on the [roadmap](../roadmap.md), deferred with its trigger.

**Also changed.** A string-valued script whose one command is the declared one is left as written instead of being rewritten into the list form: the value is compliant, so its bytes stay.
`JsonObjectWriter::readList()` reads a lone string as a one-entry list, the one-or-many shorthand composer's `scripts` accept.

**Fixtures**: two existing scenarios changed meaning and were renamed — a script running something else keeps it (`keeps-the-projects-commands`) and a string script running something else becomes a list holding both (`extends-a-string-script`) — and eight were added: a matching string script left as written, a project's command kept in place, a missing leading and a missing middle command inserted, a retired command retracted with and without arguments, a changed declaration replacing what it retires, and a declared command inserted beside the project's variant of it; the engine-level `without-a-lock-retracts-nothing` joins them.

## Changed 2026-09-29 — a declared command may accept the project's arguments

The roadmap entry "an owned composer script cannot be varied" is closed by the first of the routes it listed: prefix instead of equality, opt-in per declaration.

**What it does.** `new ComposerScript(name:, commands:, acceptsArguments: true)` lets each of the declaration's commands match when the actual command is the declared one or continues with a space and more arguments, so a project's `phpstan analyse --memory-limit=1G` counts as the declared command and keeps its flag, and the aggregate's `@` reference carries it into CI.
The space is mandatory, so `analyse` never matches `analyse-nothing`, and the tolerance is suffix-only: a wrapping prefix (`php -d memory_limit=1G vendor/bin/…`) still needs a script of the project's own.
The matching moved into a `ScriptCommand` value object, which also recognises a retired command with the project's arguments after it, the rule the previous entry recorded.
Declarations of one script keep each command's own tolerance; a command declared twice keeps the first declaration's.
`description()` names the commands that accept arguments, so the catalog and every drift line say what is tolerated rather than leaving it silent.

**Why opt-in.** Tolerance cannot tell an environmental flag from a weakening one.
Verified 2026-09-28: `phpstan analyse --level=0` on the command line overrides a config at level 9 — a real error went from "Found 1 error" to "No errors" — so a tolerant analyser command would let a flag silently defeat `PhpStanMinLevel`.
The default therefore stays exact, and a standard turns tolerance on only where it has decided the arguments are the project's to add.

**Fixtures**: a declaration accepting arguments keeps the project's arguments; the existing variant scenario is retitled for the strict default it demonstrates.
