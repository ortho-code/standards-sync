# The Rector family — decision record

Part of the [rule-model design record](rule-model.md), split out per family; the contract, the doctrine, the cross-family decisions, and the roadmap live there. Entries are chronological under their original headings.

## Decided 2026-07-23 (R3, second tool) — the Rector family

The PHPStan trio implemented a second time, deliberately, as an abstraction stress test: a second tool family shows what is tool-shaped versus general. Designed against the verified config surface of Rector 2.5.7 (read from the installed source, not recall):

- Config discovery: `--config`/`-c`, else `rector.php`, else `rector.dist.php` — two candidates, that order (`RectorConfigsResolver`), shared as `RectorConfigFile::target()`.
- The config file returns a callable. The fluent `return RectorConfig::configure()->…;` form is the documented canon (`RectorConfigBuilder` implements `__invoke(RectorConfig)`); the older `return static function (RectorConfig $rectorConfig): void {…}` remains valid — Rector's own set files use it.
- `->withSets([...])` takes file-path strings (the official `SetList` constants are path constants) — the native Tier A import: an org ships a set file, the consumer references it by path as one array entry.
- Five list-based level methods (`withTypeCoverageLevel`, `withDeadCodeLevel`, `withCodeQualityLevel`, `withCodingStyleLevel`, `withTypeCoverageDocblockLevel`): a natural int with no upper bound and no `max` alias, purely additive (a level registers the first N rules of a fixed per-category list), overshooting the list is a console warning, never an error. `withPhpLevel` is excluded from the family: it resolves the consumer's composer.json at runtime — not a statically-floorable surface.

The decisions:

- **Fluent-only scope.** A callable-style root config is refused at plan time with a convert-to-`RectorConfig::configure()` message — the inline-`includes:` precedent. Rejected: managing both styles (editing `$rectorConfig->sets([...])` too) — double machinery before a real repo demonstrates it cannot convert.
- **`RectorBaseSet`** (built as `RectorImportRule`, renamed with the naming decision below) mirrors the R2 doctrine: an absent file is created as the canonical fluent skeleton holding just the import, deliberately without `withPaths()` (the maintainer owns their parameters, as with the created phpstan config); a chain without `withSets` gains the call appended at the end of the chain; a block-form array gains the entry, matched on trimmed entry text with no quote-stripping (entries are PHP expressions like `__DIR__ . '/vendor/…'`, not bare strings — a deliberate difference from the neon rule, recorded so nobody "fixes" it); an inline single-line array is refused with a convert-to-block-form message.
- **`RectorMinLevel`** is one class over a `RectorLevelCategory` enum (the five list-based categories, mapping to the method names); the floor is a plain validated natural int. Rejected: five near-identical per-category classes, and a `RectorLevel` value object for symmetry — `PhpStanLevel` earns its existence through grammar (the `max` alias, quoted values, 0–10 bounds); Rector's level grammar is a bare natural int, so a VO would wrap no invariant. **Finding: level value objects are tool-shaped; there is no generic level to extract.**
- **`OnMissing` default is `Write` — the phpstan default inverted, by the tools' semantics.** Phpstan defaulted to `Skip` because writing was the dangerous direction (the project scalar wins the include-merge, so a written floor could lower a stricter imported level). Rector registration is additive: a written level call can only add rules, and a missing call means the category's rules are silently off — exactly what a floor exists to prevent. **Finding: `OnMissing` generalizes as a seam; its default is per-tool judgment.** *(2026-08-04: phpstan aligned on `Write`, and the seam was then removed outright the same date — under the enforce-over-silence doctrine a shipped rule always writes, and a future rule facing a genuinely owned value re-decides the question fresh. See [the revision](phpstan-family.md#revised-2026-08-04--enforce-over-silence-the-floor-creates-on-absence-and-write-becomes-the-default).)*
- **`RectorPinnedCall`** pins an exact fluent call by method name: a deviating call is rewritten to the pinned text, a missing call is appended. The pin concept shifts shape per tool (phpstan: key path + scalar leaf; rector: whole-call text); matching is textual, so formatting deviations count as drift and are normalized. Known limit, accepted: a pin cannot prevent a consumer's `withSkip()` of imported rules — enforcing the absence of specific `withSkip` entries would be a separate enforce-absence rule when a real need appears.
- **`Formats/Php/FluentChainWriter`** carries the shared mechanics — locate a call in a possibly multiline chain, replace a scalar argument, insert a block-form array entry, append a call before the terminating `;`, fail loud on anything unrecognizable. The second `Formats/` member, confirming the layer (`Rules → Formats → Core` unchanged). Still targeted line edits; no parse, no reserialization. Brackets are matched with awareness of quoted strings, so an entry like `'/a(b)'` cannot derail the scan.
- **A format's indent convention lives with the format, and an indent unit is a plain string (settled during the build).** `FluentChainWriter::INDENT` carries PHP's PER four spaces; `Core/Text/Indent` stays character-level (`TAB` exists because the escape token is invisible in source). Rejected: a `Indent::FOUR_SPACES` core constant (its name restates its value and invites `TWO_SPACES` siblings), and a character×amount structure — `Indent::detect()` returns whatever leading whitespace a file uses, including mixed units, which that structure cannot round-trip.

Two predictions confirmed at the fact level before any code: `FileTarget`'s ordered candidates fit Rector's two-name discovery exactly (R0), and the import family's per-tool split holds — a PHP array-entry edit shares nothing with a neon list edit (R2).

### Revised 2026-07-23 (post-build review) — ship the import only; park the floor and the pin

All three rules were built and green; review kept only the import. `RectorMinLevel` and `RectorPinnedCall` solve problems no consumer has yet — the "members follow as real needs appear" discipline applies to them too, and shipping them would freeze names already flagged as doubtful before any real use. What stays recorded for when a need appears:

- The floor's semantics above stand, with one design change: **no `RectorLevelCategory` enum** — the category arrives as the tool's own method name in a validated string, per the strong-typing principle this review produced (see [conventions.md](../conventions.md)): an enum re-enumerates a tool-owned open set and goes stale the day Rector ships a new category, while importing Rector's own constants would make the tool a composer dependency of every consumer (see [distribution.md](../distribution.md) on the package split). `OnMissing::Write` as the Rector default (the inversion) stands. *(2026-08-04: moot — the seam is removed; a shipped Rector floor simply always writes.)*
- The pin's semantics above stand (textual whole-call match, normalization to the pinned text, the `withSkip()` limit).
- `FluentChainWriter` ships only the array-entry operation the import needs; the scalar-replace and call-append operations return with the parked rules — no unused machinery.
- **Naming (settled 2026-07-23, after the first dogfood): rules are named as the artifact the org declares, in the tool's own vocabulary, without a `Rule` suffix** — `ManagedBlock`, `PhpStanIncludedRuleset` (param `ruleset:`), `RectorBaseSet` (param `set:`), alongside the existing `PhpStanMinLevel` / `PhpStanPinnedValues`. Why: an org config is a declaration of desired state, so artifact nouns read as declarations (`new RectorBaseSet(…)` = "this is our base set" — "base" fits the layering model, where a second-tier org ships its own base set that may nest the parent's); the `Rule` interface and the `Rules/` tree already say what kind these are; and the folder-per-rule layout makes the rule its folder's namesake, so rule-vs-support stays unambiguous (`MinLevel/PhpStanMinLevel` is the rule, `PhpStanLevel` is support). "Import" stays the family's generic term in these docs (the Tier A mechanism), per the R2 decision. **Considered and set aside, revisit welcome:** the ecosystem-style mandatory suffix (Rector's `*Rector`, PHP-CS-Fixer's `*Fixer`, CodeSniffer's `*Sniff`) — unambiguous at any distance from the declaration, but it forces mechanism-flavoured names (`PhpStanIncludedRulesetRule` stutters, pushing back to `PhpStanIncludeRule` and giving up the artifact convention); revisit if rule class names start circulating far from their declaring config or the rule-vs-support distinction bites in practice. Also rejected: `RectorSetRule` / `RectorRequiredSet` / `RectorSharedSet` (mechanism-flavoured, too heavy, or provenance-over-obligation). **The tool prefix stays despite the namespace repeating it** (`Rules/PhpStan/MinLevel/PhpStanMinLevel`): the short class name is what stands alone at the declaration site, and an org config mixes tools — unprefixed rules read ambiguously (`new MinLevel(…)` — whose?), collide across tools the moment a second tool grows a same-named rule (forcing per-consumer import aliases that reinvent the prefix inconsistently), and collide today inside `PinnedValues/`, where the rule would shadow the `PinnedValues` value object. Rector/PHP-CS-Fixer go unprefixed because each serves one tool and consumers reference FQCN strings, not side-by-side constructors. Earlier decision entries keep the names they were decided under; `ManagedBlockRule` → `ManagedBlock` and `PhpStanImportRule` → `PhpStanIncludedRuleset` applied with this decision.
- Layout refinement, applied engine-wide: **one folder per rule** — the rule class plus its supporting classes (`Rules/PhpStan/MinLevel/` holds the rule and `PhpStanLevel`); mechanism families live under `Rules/General/` (`Rules/General/ManagedBlock/`); shared per-tool knowledge stays at the tool root (`PhpStanConfigFile`, `RectorConfigFile`). Unit tests mirror `src/`; scenario tests mirror the rule folders too, each holding its test class and `fixtures/` (`tests/Scenario/Rector/Import/fixtures/…`), with cross-rule compositions in a `Family/` folder beside the rule folders.

### Revised 2026-08-02 — the set param is a path; the rule renders the entry

Raised during the ECS build and applied to both fluent base-set rules (`RectorBaseSet`, `EcsBaseSet`) in one change:

- The constructor takes the set file's path relative to the consumer project root (`set: 'vendor/acme/standards/config/rector.php'`), not PHP expression text. The rule renders the canonical entry (`__DIR__ . '/<path>'`) itself — the org author passes data, not code, which also aligns the PHP rules with the neon rule (`PhpStanIncludedRuleset` always took a plain path and owned the format's quoting).
- Gained: real validation — relative-only via `Path`, and expression-looking input (`__DIR__`, quotes) refused at construction with a pass-the-path message — instead of unvalidatable code-in-a-string that a typo would write verbatim into every consumer config.
- Narrowing, accepted: the rule can only manage `__DIR__ . '/<relative path>'` entries; a `SetList::…` constant in the consumer config is inexpressible. That matches the artifact — registering the org's shipped set file is the rule's whole job, and tool-set defaults belong in the imported set file itself (the org-author doctrine above), where org packages already declare them.
- Unchanged: the already-present check matches the (now rendered) entry text verbatim with no quote-stripping — two spellings of one path are different expressions; a deviating hand-written spelling reads as absent and the canonical entry is added beside it, as before, now less likely since the org side no longer chooses a spelling.

## Changed 2026-09-29 — the base set contributes to `withSets()`

`RectorBaseSet` implements `ContributesToList` with the list key `withSets`, per [the cross-family decision](rule-model.md#decided-2026-09-29--the-import-tier-rules-contribute-to-their-lists-and-a-replacement-takes-its-predecessors-place).
The lock records the rendered entry (`__DIR__ . '/…'`), so a moved set file is retracted and its successor takes its line, trailing comma and comment included; a set nobody declares any more is removed; declarations merge, a set declared twice counting once.
`FluentChainWriter` gained `readArrayEntries()` and `removeArrayEntries()`, and `ensureArrayEntry()` takes the entries an entry replaces; its array scan is shared by all three.
A spelling the lock never recorded is still the project's: a hand-written variant of the entry stays beside the canonical one, as before.
