# The psalm family — decision record

Part of the [rule-model design record](rule-model.md), split out per family; the contract, the doctrine, the cross-family decisions, and the roadmap live there. Entries are chronological under their original headings.

## Agreed 2026-08-02 (R3, fourth tool) — the psalm family: the first XML tool, and the first with no import

Chosen over deptrac the same date, deliberately for being the most different family on the board — each R3 phase is an abstraction stress test, and psalm stresses three new dimensions at once:

- **The first XML config** (`psalm.xml`). The 2026-07-16 block-format decision already refused XML for the marker family (the grammar draws comment-lead lines; create-from-nothing yields a rootless fragment, append-at-end lands after the root close tag) and said structured rules are the right tool there — psalm is that case arriving. It forces the first `Formats/Xml` member: targeted attribute rewrites on the `<psalm …>` root and child-element insertion copying the file's indentation — still no parse-and-dump (the recorded anti-goal: reserialization destroys the consumer's formatting and comments), fail loud on anything unrecognizable.
- **The first family with no Tier A.** Psalm has no native "extends another psalm.xml", so nothing rides `composer update`: every shareable value is a synced value, and the standard propagates only on sync runs. This also breaks the phpstan floor discipline's shape — there is no imported ruleset to carry the level, so the guard's `OnMissing` choice needs fresh judgment (open design question, alongside what a created-on-absent config should hold, if creation is even wanted for a tool whose config is mostly per-repo).
- **An inverted level scale.** Psalm's `errorLevel` runs 1 = strictest to 8 = loosest (to be verified from the installed source at design time), so the org guard is numerically a *ceiling*: enforce `errorLevel ≤ N`, lower a looser value, never touch a stricter one. Confirms the R3 finding a third time: level value objects are tool-shaped; there is no generic level to extract.

Known and accepted going in: the June inventory rated psalm the weak candidate — "no native extends… you'd share ~20% of the file" (`errorLevel`, `<plugins>`, default `<issueHandlers>`; the bulk — `<projectFiles>`, `<ignoreFiles>`, `errorBaseline` — is per-repo). The phase is chosen for abstraction coverage, not leverage; real demand exists regardless (every repo in the first consumer org owns a standalone `psalm.xml`). Candidate first tranche, settled at design time: the error-level ceiling guard and a plugin enforce-presence rule; pinned root attributes if a real value asks for it.

Psalm is installed nowhere in this development setup, so the design phase opens by adding it to a test package and reading the verified config surface from the installed source (config discovery order and `.dist` variants, the level grammar, plugin registration, issue-handler shape) — never from recall.

### Designed 2026-08-04 — two rules over the first XML writer; enforcement without abstention

Designed against the verified surface of psalm 6.16.1, installed in the update-path test consumer — the engine's own require-dev cannot host psalm (6.14+, the first PHP 8.5-compatible line, needs `sebastian/diff` ≤ 8 where phpunit 13 locks 9). Build pending; the doctrine half was validated first on the phpstan family ([the enforce-over-silence revision](phpstan-family.md#revised-2026-08-04--enforce-over-silence-the-floor-creates-on-absence-and-write-becomes-the-default)).

**Verified facts (installed source):**

- Discovery: `--config`/`-c`, else `psalm.xml`, `psalm.xml.dist`, `psalm.dist.xml` in that order (`Config::DEFAULT_FILE_NAMES`), searched upward through parent directories — the upward walk is irrelevant to sync; the three candidates map onto `FileTarget` exactly.
- Every config load validates against the shipped `config.xsd`; schema errors throw and psalm refuses to run (a missing `xmlns` on `<psalm>` is tolerated — injected in memory before validating). Consequence: a synced file must stay XSD-valid, and the XSD is the grammar authority.
- Root children are order-free (`xs:choice`, each element at most once) — insertion position is structurally free — but **`<projectFiles>` is required**, which decides the created-config question below.
- `errorLevel`: root attribute, integers 1–8 strictly validated, no aliases; **an absent attribute means level 2**; direction confirmed in the reporting code (an issue whose intrinsic level is below the config level is downgraded to info): 1 = strictest, 8 = loosest — the org guard is numerically a ceiling, semantically a strictness floor. Third confirmation of the R3 finding: level value objects are tool-shaped.
- Psalm's own generated config opens the root tag across multiple lines — the XML writer handles a multiline open tag from day one.
- The parked plugin surface, recorded for the future member: one optional `<plugins>` child holding `<plugin filename="…"/>` (repo-local) and `<pluginClass class="FQCN"/>` (composer packages — the shareable form; child elements are plugin config); enforce-presence matches on the `class` attribute. `<issueHandlers>` (per-issue elements, `info|error|suppress`) is the future pin-like surface.

**The decisions:**

- **The family enforces without abstention** — every psalm rule creates the config on `null`, so a declared rule is always enforced and `withoutRule()` is the opt-out. No umbrella machinery: the first psalm rule in the fold meets `null` and creates; every later rule receives real content. Rejected on the way: abstain-on-absent for the level guard (a declared rule could sit silently unenforced — the same reasoning as the phpstan revision), and a plan-time "family requires the base config" invariant (a new cross-rule seam that would also fight the `withoutRule()` ladder; there is nothing to forget when every rule self-creates).
- **`PsalmBaseConfig`** (param `config:`) seeds a project that has no config with the org's template — `templates/psalm.xml`, read through `Package` — verbatim, and never edits an existing config. Declared first, it overrides the engine skeleton for the whole family. The authoring insight this family sharpened, worth repeating in the authoring guide: **for a tool with no import tier a template is one-shot — only values that also have their own rule stay enforced.** The template bootstraps; rules converge. ("Floors, not copies" applied: the template is the permitted copy, firing only into nothingness, so it can downgrade nothing.)
- **`PsalmConfigFile::createConfig()`** is the engine's minimal skeleton for any psalm rule that must create — a code constant, the Rector/ECS `createConfig()` precedent. One recorded deviation from those skeletons: it names project paths (`src`, ignoring `vendor` — psalm's own init default), because the XSD requires `<projectFiles>` and an omitting skeleton would be a config psalm refuses to load; the maintainer verifies the paths. Set aside: a distributed skeleton file (org-overridable by shipping a same-named file) — it would need engine self-location machinery for no behavioural gain; noted as a possible later improvement.
- **`PsalmLoosestErrorLevel`** (param `loosest:`; folder `Rules/Psalm/LoosestErrorLevel/` with the `PsalmErrorLevel` value object — bounds 1–8, `createDefault()` = 2, `isAtMost()`): a looser written level is lowered to the limit, a stricter or equal one never touched; **an absent attribute is made explicit** — it means 2, so 2 is written, or the limit when the limit is stricter; on `null` it creates the skeleton at the limit, so bootstrapped configs start at the org standard. **No `OnMissing` anywhere in the family** (moot since the seam's same-date removal — the phpstan revision; the observation stands as the reason psalm never needed it): the seam existed for include-blindness, and a tool with no import tier and a defined absent-value default has no unknowable effective value. Implements `ExplainsDrift`, wording carrying the inverted scale ("looser than the loosest allowed"). Naming: `PsalmMaxErrorLevel` and `PsalmErrorLevelCeiling` rejected (numeric direction words on an inverted scale read as the opposite of the semantic strictness floor), `PsalmErrorLevelLimit` rejected as less literal; "loosest" states the declared artifact exactly — the loosest level the org allows.
- **`Formats/Xml` opens with attribute operations only** (class name at build, working candidate `XmlElementWriter`): read/replace/insert an attribute on a named element's possibly-multiline open tag — quoting and layout preserved, comment-aware scan, fail loud on a missing or unterminated open tag and duplicate attributes. No parse-and-dump (the recorded anti-goal). Child-element insertion returns with the plugin member.
- First tranche ships exactly these two rules; the plugin member and pinned root attributes stay parked until a real value asks. Consumer wiring at build: org-cs ships `templates/psalm.xml` with an explicit `errorLevel`, and an org test pins the template's level at-or-stricter-than the declared limit — the phpstan pin-test discipline transposed.
