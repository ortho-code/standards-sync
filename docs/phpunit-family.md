# The phpunit family — decision record

Part of the [rule-model design record](rule-model.md), split out per family; the contract, the doctrine, the cross-family decisions, and the roadmap live there. Entries are chronological under their original headings.

## Agreed 2026-08-14 (R3, eighth tool) — the phpunit family: the leverage pick, replaying the psalm shape

Promoted from the roadmap's candidate list as recorded there: the cheapest remaining family — XML (the writer exists), dist candidates (the resolution policy covers them), and no import tier, so it replays the psalm shape: a template base config plus value rules over the root's strictness attributes. High leverage, near-zero new abstraction coverage. What little it does stress: the first *reuse* of `XmlElementWriter` outside the family it was built for (the `FluentChainWriter`-reuse test the ECS family ran, transposed to XML — and since root attributes need no new `Formats/` member, no backend re-assessment falls due), and the first tool whose enforcement teeth are an exit code rather than a load refusal. This entry records the verified config surface the design phase opens with, and the open questions it leaves.

**Verified facts (phpunit 13.2.4 in the base org test package and 12.5.33 in the engine's own require-dev — the psalm-compat pin; every fact read from both installed sources and probed live on both, never from recall):**

- **Discovery is working-directory-only, three candidates** (`XmlConfigurationFileFinder`): `--config`/`-c` wins (a directory argument is searched like the cwd), else `phpunit.xml`, `phpunit.dist.xml`, `phpunit.xml.dist` in that order, first existing file wins, no upward walk through parent directories (psalm has one). The list maps onto `FileTarget` exactly and carries **two dist variants** — both spell the dotted `dist` segment, so the resolution policy classifies both, and a repo holding both meets the standing same-side refusal; rightly, since phpunit itself would silently read `phpunit.dist.xml` and never look at `phpunit.xml.dist`. Creation on the first candidate (`phpunit.xml`) matches the tool's own behaviour: `--generate-configuration` writes exactly that name.
- **Validation warns and fails the run; it does not block it.** Every load validates against the shipped XSD for the running series (`Loader` → `Validator`), but a `<phpunit>`-rooted document with validation errors still loads and the tests still run: the errors surface as a test-runner warning ("Test results may not be as expected because the XML configuration file did not pass validation"), and because `failOnPhpunitWarning` defaults to true the run **exits 1** — probed on both versions with an unknown attribute: tests green, exit 1. A document that instead validates against an *older* shipped schema triggers a migrate-configuration deprecation (not failing by default; `failOnPhpunitDeprecation` defaults false); only a non-`<phpunit>` root matching no schema at all refuses to load. Softer teeth than psalm's refusal, but teeth: a synced config that broke schema validity would fail every consumer's default run.
- **No namespace.** The config is namespace-free and `xsi:noNamespaceSchemaLocation` is optional (the probe config omitted it and validated) — fixture validation is a plain `schemaValidate` against the shipped `phpunit.xsd`, without the xmlns injection the psalm validator replicates.
- **The root attribute surface** (`configAttributeGroup`): 61 attributes on 13, mostly `xs:boolean`; 12 has the same set minus `diffContext`, `requireCoverageContribution` and `requireSealedMockObjects`, and no shared attribute differs in type or default between the versions. An absent attribute means its documented default — the loader's hardcoded fallbacks spot-checked against the XSD defaults. The non-false boolean defaults: `failOnPhpunitWarning`, `beStrictAboutTestsThatDoNotTestAnything`, `cacheResult`, `resolveDependencies`.
- **The loader's boolean grammar is narrower than the XSD's.** `booleanFromString()` accepts case-insensitive `true`/`false` only; every other spelling silently reads as **false**. `xs:boolean`'s lexical space also admits `1`/`0`, so `failOnWarning="1"` schema-validates cleanly (probed via `schemaValidate`) while phpunit reads it as false — a validity check cannot catch it, and the flag is off with no warning anywhere. A value rule must write the `true` spelling and treat every other spelling as drift.
- **No import tier, confirmed:** nothing in the XSD or the loader references another phpunit config — `<source>`'s include/exclude are coverage paths, `extensionsDirectory` loads PHAR extensions. Everything shareable is a synced value; the standard propagates only on sync runs.
- **All root children are optional** (`xs:all`, every element `minOccurs="0"`): a bare `<phpunit/>` is schema-valid — unlike psalm's required `<projectFiles>`. But a config without `<testsuites>` makes a bare `vendor/bin/phpunit` print usage and exit 1 (probed), so a *useful* created config names a test suite — psalm's named-paths skeleton deviation transposed: name the conventional directory, the maintainer verifies.
- **phpunit's own generated config** opens the root tag across multiple lines — the multiline handling `XmlElementWriter` was born with is needed here too — and carries the tool's recommended strictness set: `executionOrder="depends,defects"`, `requireCoverageMetadata`, `beStrictAboutCoverageMetadata`, `beStrictAboutOutputDuringTests`, `displayDetailsOnPhpunitDeprecations`, `failOnPhpunitDeprecation`, `failOnRisky`, `failOnWarning`, plus a `<source>` element with `ignoreIndirectDeprecations` and notice/warning restrictions. Template material, and the tool's own opinion of what strictness means.

**Expected shape**, to be settled at design time: `PhpUnitBaseConfig` (template seed, the `PsalmBaseConfig` precedent — one-shot bootstrap, rules converge) plus value rules over root strictness attributes; enforcement without abstention per the doctrine, creating on `null` like every psalm rule. The XML no-comment verdict applies unchanged — `ExplainsDrift` and the generated catalog carry the explanations. Fixture validation grows a phpunit tier beside the psalm one: schema-validation against the shipped `phpunit.xsd`, loud when the schema's package is missing per the 2026-08-12 revision.

**Open questions for the design phase, recorded at the agreed stage:**

- **The tranche.** Which attributes the org enforces is the org-shaped choice needing worked examples: the generator's recommended set above is the tool's own opinion; the `failOn*` family (warnings, deprecations, notices) and `beStrictAbout*` family are the org-standard candidates. Whether the first cut is boolean-only, and how many rules it is, is the shape question below.
- **The rule shape: per-attribute rules or one generic root-attribute pin.** The attribute list is phpunit's open surface — 61 names and growing — so a closed enum is out by the strong-typing convention; a generic `(attribute:, value:)` pin over validated primitives against per-semantic rules (a boolean that pins true, an integer that floors) is the psalm-vs-phpstan-pins trade-off replayed, and the boolean-spelling wrinkle above must be drift under whichever shape wins.
- **The version-skew guard.** Enforcing a 13-only attribute (`requireCoverageContribution`, …) makes a phpunit-12 consumer's every run exit 1 — the unknown-attribute warning above. The tranche must stay within every phpunit major the org supports, or the org's composer family requirement must pin the major; where that knowledge lives (the org's judgment, or a rule-level guard) is a design call.
- **Absent-versus-explicit on compliant defaults.** Enforcing true on an attribute whose default is already true (`beStrictAboutTestsThatDoNotTestAnything`): write it explicit — the psalm make-explicit precedent, robust against upstream default changes — or leave absence compliant. One answer per family, decided once.
- **Non-boolean and child-element surfaces.** `executionOrder` (an ordered keyword list), the timeout integers, and `diffContext` are value rules with their own semantics; the `<source>` strictness attributes sit on a child element, and creating that element needs the child-element insertion parked since psalm's plugin member. Both are candidates for parking — the template can still seed them one-shot, which is exactly the template-bootstraps-rules-converge insight.

### Designed 2026-08-14 — a template seed and one pinned-attributes rule; the rule boundary follows the declared artifact

The design phase, run the same day over the verified surface above. Two rules, both transposing existing shapes; no new `Formats/` work.

**The decisions:**

- **`PhpUnitBaseConfig`** (param `config:`) is a `PsalmBaseConfig` twin to the word: seed a config-less project with the org's `templates/phpunit.xml` verbatim, never edit an existing config, refuse an empty template. The duplication is deliberate — the R2 import-family reasoning: a general template-seed rule taking a free target could point a psalm template at `phpunit.xml`, the mismatch per-tool classes make inexpressible. A shared base stays parked until a third member argues for it.
- **`PhpUnitPinnedAttributes`** (param `attributes:`, a `name => value` map), one rule holding the org's whole pinned set — the `PhpStanPinnedValues` shape, flat instead of nested, so a `PinnedAttribute` value object (validated XML name; bool rendered `true`/`false`, int as decimal text, empty values refused) with no collection object around it. Enforcement without abstention: on `null` it creates the engine skeleton and pins into it. Comparison is text-exact — even a spelling phpunit happens to read correctly (`TRUE`) normalizes, deliberately: one canonical spelling, zero per-attribute type knowledge. Encoding refusals stay the writer's.
- **The rule boundary follows the declared artifact** — the principle behind the shape choice, previously visible only as precedent, recorded here on request: the phpstan pins are *one declared artifact* (a nested map mirroring the config's own structure, no per-pin behaviour or report story) and so are one rule; the composer requirements are *N independent declarations*, each with its own semantics (constraint raising, section moves, per-package explanations) and so are N instances of one class. The phpunit flags are the map case, flat: one declared standard, every entry behaving identically. Rejected: a per-attribute generic rule — its real advantage is acknowledged (a predicate disable removes one attribute while the remaining pins stay org-owned, where replacing the collection wholesale freezes a consumer-side copy against org evolution), but it serves per-attribute consumer deviation, which the pin tier is defined to exclude — a value consumers may legitimately deviate on belongs in the template, and deviating from a pin is a conversation with the org. Also rejected: per-attribute semantic classes (an open 61-name surface; the strong-typing convention).
- **`ExplainsDrift` is adopted, diverging from `PhpStanPinnedValues`** — there the diff is self-evident; here the spelling trap is not (a maintainer seeing `failOnWarning="1"` → `"true"` cannot know `"1"` was silently off). The explanation appends the reads-as-false clause only when the pin is boolean-shaped (`true`/`false`) *and* the written spelling is neither, case-insensitively — the rule cannot know an open surface's attribute types, and a boolean-shaped pin is the evidence it needs.
- **The skeleton** (`PhpUnitConfigFile::createConfig()`): root plus `bootstrap="vendor/autoload.php"` and one `default` suite on `tests` — phpunit's own generated defaults; the psalm named-paths deviation transposed with a usage-driven reason (nothing is XSD-required, but a suite-less config makes a bare run print usage and exit 1); the maintainer verifies the paths. Single-line root open tag — pins insert inline; the pretty multiline shape belongs to the org template, which wins whenever it is declared first.
- **The org requirement floor is `^12`, coupled to a shared-set tranche.** The org's composer family will require `phpunit/phpunit: ^12` (a minimum: a 13 consumer keeps `^13`), and every pinned attribute must exist in every major the floor allows. The stronger reason, from review of this design: the org's required tool set already carries `vimeo/psalm: ^6`, and psalm 6.14+ — the first PHP 8.5-compatible line — conflicts with phpunit 13 over `sebastian/diff` (the verified fact behind the engine's own 2026-08-12 downgrade), so a `^13` floor would make the org's required tools composer-unresolvable on PHP 8.5. Both floors — the org requirement and the engine's dev pin — lift together when psalm's cap moves.
- **The org tranche (wiring phase): `failOnWarning`, `failOnDeprecation`, `failOnRisky`, `beStrictAboutOutputDuringTests`, all `true`** — shared-set booleans whose defaults are false, so every consumer's runs gain real gates. *(Widened at wiring, same date: `failOnEmptyTestSuite` joined as the fifth pin — see the wired note.)* Declined for now, recorded as candidates: `failOnNotice`, `displayDetailsOnAllIssues`, `executionOrder="depends,defects"`. The template additionally seeds — one-shot, unenforced — `cacheDirectory`, the suite layout, and the `<source>` element with the generator's restriction attributes (`ignoreIndirectDeprecations="true"` keeps dependency deprecations from tripping `failOnDeprecation`).
- **The check script gains `vendor/bin/phpunit`** (wiring phase) — the composer family's point: synced strictness flags enforce nothing until CI runs the tests. A consumer with no tests fails the check, accepted as enforce-over-silence; what a configured-but-empty suite does exactly is verified live in the test consumers before this lands.
- **`Testing/Validation/PhpUnitConfigValidator`** joins the fixture tier beside the psalm validator: plain `schemaValidate` against the installed phpunit's shipped `phpunit.xsd` for the three config names — no xmlns injection — loud on a missing phpunit per the 2026-08-12 revision, availability injectable (`phpunitInstalled:`).

**Build scope:** `Rules/PhpUnit/` (`PhpUnitConfigFile`, `BaseConfig/PhpUnitBaseConfig`, `PinnedAttributes/PhpUnitPinnedAttributes` + `PinnedAttribute`), the validator plus its default-list entry, unit coverage per conventions, and the scenario fixtures: rewrite a deviating value, normalize the `"1"` spelling (the trap, catalog-pinned), insert into a single-line and a multiline root tag, leave a compliant config byte-identical, create from nothing; the BaseConfig seed/never-edit pair; the Family from-scratch (template first, wins over the skeleton) and converge-existing pair. Org wiring follows as its own phase.

**Built 2026-08-14**, as designed — all suites and deptrac green on the first run, `XmlElementWriter` reused without any change (the cross-family reuse the promotion predicted, the ECS-for-`FluentChainWriter` result repeated on XML). Build notes: `PhpUnitPinnedAttributes::apply()` has no compliant branch — the writer's byte-identity early-return serves rewriting, normalizing, inserting and leaving alike (the psalm floor's shape); the unit catalog additionally pins that a spelling phpunit happens to read correctly (`TRUE`) normalizes too, and that the trap clause stays off a deviation between recognized spellings (`false` where `true` is required). The Family converge fixture carries a consumer comment above the root tag, riding the writer's comment-skip.

**Wired 2026-08-14** — the first consumer org ships `templates/phpunit.xml` (the generator's recommended shape, carrying every pinned flag) declared ahead of the pins, pins the four agreed flags, requires `phpunit/phpunit: ^12`, and appends `vendor/bin/phpunit` to the check script; the transposed pin test reads each template attribute through the engine's writer and asserts it equals its pin. Live-loop verified in both test consumers. Update path: the sync created the template byte-identically and added the requirement plus the script entry; completing the install resolved phpunit 12.5.33 beside psalm 6.16.1 — composer downgraded the shared `sebastian/diff` from 8 to 7 on the way, the exact conflict surface the `^12` floor decision reasoned from — phpunit loaded the synced config, a second sync reported everything in sync, and the result was committed as the new baseline. Adoption path: the family arrived through the second-tier org's `include()` with no wiring of its own, the created config byte-identical to the base template. All three dist-resolution scenario branches were rebased onto the new baseline and hold their committed expectations. Residual found and closed the same date: with a synced config in place, a consumer *without* a `tests/` directory fails the check loudly (exit 2, "Test directory … not found"), but an existing-but-empty `tests/` directory passed with "No tests executed!" and exit 0 — so `failOnEmptyTestSuite` joined the pins as the fifth flag (verified live: the empty suite now exits 1), widening the agreed tranche by one on review of the wired result. The other declined add-ons stay recorded in the design entry.
