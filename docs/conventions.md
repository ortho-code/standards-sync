# Code and test conventions

- PHP 8.5+, `declare(strict_types=1)` in every file. Use modern features freely (`readonly class`, enums, `new` in initializers) — including the newest stdlib: `array_find` / `array_any` / `array_find_key` over a stateless `foreach` scan; a scan that tracks running state stays a `foreach`.
- Single quotes unless interpolation or escapes need double.
- Comments in English, one sentence per line; comment the non-obvious *why*, not the *what*.
- **Comments own only their holder's knowledge (recorded 2026-08-06).** A declaration's docblock states what the value or type *means* — its contract, which stays even when a collaborator computes the value. The moment it narrates a producer's action, a collaborator's policy or justification, or one caller's situation, knowledge has crossed a boundary: move the sentence to the class that decides it, or delete it when the surrounding type already implies it. Specific vocabulary on general code is the visible symptom; policy narration in neutral words is the same violation and harder to spot.
- CLI (`Presentation/Cli`, `symfony/console`): `bin/standards-sync` keeps only the autoload probe, then builds and runs the console application.
- **Adapters**: encode the backing technology in the class name only where a port has interchangeable implementations (`SymfonyFilesystem`, `InMemoryFilesystem`); the single CLI delivery stays undecorated. Group adapters by capability (`Filesystem/`, `Cli/`), not per-vendor subfolders (one class per vendor → alias noise).
- **Rules are named as the artifact they declare**, in the tool's own vocabulary, without a `Rule` suffix (`ManagedBlock`, `PhpStanIncludedRuleset`, `RectorBaseSet`); constructor parameters follow the same vocabulary (`ruleset:`, `set:`). The rule is its folder's namesake; supporting classes share the folder. Discussion and the set-aside suffix convention: the 2026-07-23 revision note in [rector-family.md](rector-family.md).
- **Exceptions**: SPL types, message built where the condition is detected. A domain exception for plan-time refusals (one class per *meaning*, named constructors per case — `::callableStyle()`, `::inlineArray($method)`) is parked until the CLI needs to render a refusal as a user-fixable error distinct from an engine bug — decide it together with whether a refusal aborts the run or becomes a per-file report entry.
- **Verify, don't recall — and that includes our own record (recorded 2026-08-11).** Every claim about another tool's behaviour — its config surface, its resolution rules, what it does with a value we write — is read from the installed source or settled by a probe, and the entry recording it says which. This governs any such claim at any point in a phase: one made while designing or reviewing counts as much as the survey that opens a family, and "the research is done" is not a licence to start asserting. The same reflex applies to decisions recorded in these docs — re-read the entry rather than remembering it, because a remembered invariant drifts wider or narrower than the one that was written. The tell is inverted from what it should be: a claim that feels too obvious to check is the one most worth checking, since facts that read as tool trivia get verified as a matter of course while the ones that read as common knowledge slip through (which requirement section "wins" when a package sits in both; what the deletion invariant actually covers — both were asserted and both were wrong).
- **Re-assess format backends regularly.** The hand-rolled `Formats/` writers are a choice, not an identity: at every new `Formats/` member — and immediately when a writer produces a corruption-class bug or outgrows the targeted-edit bargain — re-assess a parser-backed backend (position-aware ASTs: nette/neon's token-positioned nodes, nikic/php-parser's format-preserving printing). Rules depend only on the `Formats/` API, deptrac-enforced, so a backend swap is internal; its acceptance bar is the scenario suite passing with zero fixture changes. A candidate backend is judged on capability and that bar alone — the dependencies it would add are no counter-argument. Synced output is parse-validated in tests (parsers sit in require-dev); a synced file whose parser is missing fails loud rather than skipping.
- **Apply verified architecture retroactively.** Once a decided principle or layer has proven itself (a `Formats/` writer serving a second family, a validation home, a naming rule), sweep existing code that predates it in its own small, behaviour-preserving phase — don't leave legacy shapes waiting for "next touched". This is distinct from creating a *new* abstraction, which still waits for the evidence of real concrete cases (never first): applying existing, verified architecture needs no second user.
- **Contract-first on the consumer surface, never-first behind seams (recorded 2026-08-06).** Never-first governs internal machinery only. Anything consumers implement, construct, or hold — the `Rule` contract, `FileTarget`, the `Authoring/` API, rule constructors — gets its shape decided *now*, with the test: would a later fix be additive or breaking? (Widening a parameter type breaks every implementor while widening a return type does not — the reasoning that put `apply(?string)` and `FileTarget` into the R0 contract with zero rules written.) Machinery behind deptrac-enforced seams (format writers, report internals, resolution) can swap without consumers noticing, so generalizing it early is pure weight — the prior attempt's universal parse-and-merge framework is the cautionary record. At the open-sourcing milestone, a BC-surface audit marks what is API and what is internal, before any compatibility promise is made (see the roadmap in [rule-model.md](rule-model.md)).
- **Strong typing ends at other tools' surfaces.** Enums, bounded value objects, and closed case lists are for value spaces we own or that are genuinely fixed. A third-party tool's own surface — its method list, its level categories, its bounds — is an open set that grows with the tool's releases: hardcoding it as a closed type makes the package stale the day the tool ships something new, and importing the tool's constants instead would make the tool a composer dependency of every consumer (see [distribution.md](distribution.md)). Model such inputs as validated primitives (a method name string, a natural int).
- **Value objects**: single-value wrappers (`Path`, `Label`) expose one neutral accessor `value()`; composites (`Change`, `RuleApplication`, …) expose one getter per field named for the field (`path()`, `before()`); turning a composite into one string is `toString()` or a dedicated formatter, never a field getter. No public properties; no implicit `(string)` cast or `__toString`.
- **Named constructors**: `from<Source>()` when parsing or converting input (`Path::fromString`); `create()` / `create<Variant>()` when constructing with defaults (`SyncConfig::create`). Instance evolution is `with*()` returning a new instance. A value object's constructor stays private behind its named constructors. Semantics that don't fit either prefix belong on the type (class docblock), not in a novel factory name — a reader must be able to tell a factory from a getter at a glance. The prefixes govern every static method that produces a value — plain helpers returning strings included (`FileContent::fromString`), not only constructors returning `self`; borrowed idioms like `of()` or `make()` don't say which they are.
- **Tests**: three phpunit suites — `tests/Unit` (pure logic), `tests/Integration` (touches the real filesystem or wires a component), `tests/Scenario` (the end-to-end fixture catalog; classes extend `ScenarioTestCase`). One scenario per test method; parametrize families with a `#[DataProvider]` written as a generator (`yield 'case' => [...]`), not a returned array. Several assertions verifying one scenario are fine; distinct scenarios get their own case.
- **File-content fixtures in tests are nowdocs**, built via `Testing\FileContent::fromString()` (appends the trailing line break) — no `\n`/`\t` escape tokens in test strings; the body reads exactly like the file, real tabs included. Layout: the `<<<'NEON'` opener on its own line, the body and the closing marker one level deeper than the opener, the `)` on the next line — PHP strips exactly the marker's own indentation, so a uniformly prefixed body comes back intact, real tabs included. Single-line strings without a newline stay plain strings.
- **The scenario suite is the behaviour catalog.** Scenario tests mirror the rule library — one folder per rule holding the test class and its `fixtures/` (`tests/Scenario/PhpStan/Import/`), with cross-rule compositions in a `Family/` folder beside them and engine-level pipeline behaviours that are not any rule's own (target resolution) under `tests/Scenario/Engine/` — and cover every pipeline behaviour (first-sync adoption, block updates, marker syntaxes, hierarchy via `include()`, multi-file and subdirectory paths) and double as the worked examples for consumers and the outline for the usage docs. **Any change to core pipeline behaviour must add, update, or remove the matching fixture.** When you touch the engine fold, a rule type, first-sync handling, or marker handling, ask which fixture demonstrates it and whether it still holds. Prefer too many scenarios over missing one.

## Commands

- Tests: `composer app-run-tests` (all three suites), `composer app-run-tests-unit`, `composer app-run-tests-integration`, `composer app-run-tests-scenario`.
- Test strictness (fail on any warning/deprecation/notice/risky, stop on first defect) lives in `phpunit.xml.dist`, not in the scripts.
- Architecture: `composer deptrac` — fails on any cross-layer violation or uncovered class.
