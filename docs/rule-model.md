# Direction: a rule-based model

**Status:** built through R3's second tool family (2026-07-23) — the engine folds rules per [the `Rule` contract](#decided-2026-07-15-r0--the-rule-contract); the rule library covers the block family, the PHPStan family (import, level floor, pins), and the Rector import (see [the 2026-07-23 decision](rector-family.md#decided-2026-07-23-r3-second-tool--the-rector-family) and its revision note — the Rector floor and pin are designed but parked until a real need). The ECS family (third tool) is built — see [the 2026-08-02 decision](ecs-family.md#decided-2026-08-02-r3-third-tool--the-ecs-family); the same date moved the base-set rules' `set:` param from PHP expression text to a plain relative path (revision note under the Rector decision), and built the install-location resolution layer as config-build-time self-location through composer's install record (`Authoring/`: `Package` + `Standard` — see [the revision](#revised-2026-08-02-built--config-build-time-self-location-the-authoring-layer) under the layer decision). On 2026-08-04 the phpstan floor was aligned with the enforce-over-silence doctrine — create-on-null and an always-written floor, the `OnMissing` seam removed the same date (see [the revision](phpstan-family.md#revised-2026-08-04--enforce-over-silence-the-floor-creates-on-absence-and-write-becomes-the-default) under the first-member decision) — and the psalm family (fourth tool) is built — two rules over the first `Formats/Xml` writer (see [the design note](psalm-family.md#designed-2026-08-04--two-rules-over-the-first-xml-writer-enforcement-without-abstention) and the built notes under it), completed 2026-08-05 with the fixture XML/XSD tier and the first consumer org wired. Multi-file config resolution is built (2026-08-06): several existing candidates resolve by the dist policy — the dist file wins over a shadowing non-dist, reported on every run; same-side ambiguity refuses (see [the decision](#decided-2026-08-05--resolution-prefers-the-dist-candidate-same-side-ambiguity-refuses)). The pre-rename history (baseline and earlier takes) is preserved in the private predecessor repository.

## The goal

Share coding-standards config across many repos from one package, keep it updated automatically (no manual copy-paste), and support the full range of config a project accumulates — `.editorconfig`, `.gitignore`, static-analysis configs (PHPStan / Rector / …), framework config, and more — each with its own format and mechanism.

## Three tiers of sharing (by what the format allows)

- **Tier A — native import / extends.** The format can reference shared config (PHPStan `includes`, Rector `require`, ESLint import, tsconfig `extends`, framework config imports, composer-required PHP config). Sharing = ship the real config in the package + a one-line import in the repo; it rides `composer update` with no markers, no sync step, no drift. Biggest surface, cheapest mechanism.
- **Tier B — structured merge.** Parseable files with no import (`composer.json` / `package.json` scripts, XML configs): own specific keys, leave the rest.
- **Tier C — opaque text.** No import, no structure to key on (`.editorconfig`, `.gitignore`): managed marker blocks or line-level rules. Smallest, lowest-velocity tier.

Priority is A → B → C by value. The first build targeted C (managed blocks); the direction below unifies all three under one abstraction.

## The `Rule` abstraction

A `Rule` is the unifying primitive. It targets one file and **applies** itself as a pure content transform — idempotent, a no-op when already satisfied. Drift (`--check`) is **derived**, not hand-written: a rule is satisfied exactly when applying it changes nothing (see the pre-R0 decisions below). Rules compose by folding over a file's content one after another, with a single final write (the existing pure pipeline is kept).

Rule *types* map onto the tiers:

- **`ManagedBlockRule`** — places a template as a managed marker block. This is the current block engine, reframed as one rule type; it handles Tier C today.
- **`ImportRule`** — ensures a one-line import / require / extends is present (Tier A). *(Realized per tool from R2 on — `PhpStanImportRule` first, with "import" as the family's generic term; see the R2 decision.)*
- **`KeyRule` / structured rules** — read / check / set a specific key in a parseable file (Tier B). These are **value-aware**, not blind sets: e.g. a *floor* — "PHPStan level ≥ 6: raise it if lower, leave it if already higher" (never weakens a stricter project) — plus list-unions, ceilings, enforce-presence, enforce-absence. This is where rules beat both a dumb copy (which would *downgrade* a level-9 project) and a plain import (which ships a default the consumer can silently drop below — a floor rule *enforces* the minimum). Each such rule does **narrow, targeted** parsing of its one key with existing format libraries; there is **no universal parse-and-merge framework** (that was the weight that sank the prior attempt — see [prior-approaches.md](prior-approaches.md)).

New rule types — and eventually community-contributed ones, as with the Rector / ECS rule libraries — extend the set without touching the pipeline.

Value-aware rules are the real payoff of Tier B and a strong argument for the whole direction; "raise PHPStan level only if lower" is a good first Tier B target once the abstraction exists.

**Positioning — "floors, not copies" (2026-07-15).** This is the product pitch and the README's opening example once docs land. It also explains in one line why the alternatives fall short: a copy *downgrades* a stricter project, an import ships a default the consumer can silently drop below — a floor rule *enforces* the minimum.

## Prior art (studied)

Three mature PHP tools converge on the same decomposition, deliberately split across separate seams rather than one fat interface:

- **Rector** — `RectorInterface` = `getNodeTypes()` (what to act on) + `refactor()` (act, or return `null` for "no change"). Configurability is a *separate* `ConfigurableRectorInterface::configure(array)`. The description + a mandatory before/after code sample live on yet another interface. Ordering: none — it re-runs to a fixpoint, so rules must be idempotent.
- **PHP-CS-Fixer** — `FixerInterface` = `isCandidate()` / `supports()` (cheap gate) + `fix()` (mutate in place) + `getDefinition()` (mandatory doc + sample) + `getPriority()`. Config via a *separate* `ConfigurableFixerInterface` with a self-describing, validated schema. Ordering: a single global integer priority — its known pain point.
- **PHP_CodeSniffer** — `Sniff` = `register()` (token types) + `process()` (report through the file, don't return findings). Config via plain public properties set by reflection from `ruleset.xml`. Ordering: none — analyzers don't interfere.

Convergent lessons for our `Rule`:

1. **Keep the base contract tiny** — target + `check` + `apply`. Config and docs go on separate seams, not the base.
2. **Separate `check` from `apply`** — `check` gives drift / `--check`; `apply` is idempotent and no-ops when already satisfied. *(Superseded 2026-07-15: we derive check from apply instead of hand-writing it — see the pre-R0 decisions below. The lesson's substance, apply no-oping when satisfied, stands.)*
3. **Config is opt-in** (`ConfigurableRule`), passed whole (replace-not-patch), defaults owned by the rule, and **typed / validated** (a per-rule immutable value object) rather than an untyped array.
4. **Each rule carries a description + a before/after sample**, which doubles as its test fixture.

## Decided 2026-07-15 (pre-R0) — contract, identity, absence

Settled in discussion ahead of R0; the R0 contract below turned these into the actual interface, tested against the three probes.

### No hand-written `check()` — drift derives from a pure `apply`

`Rule` has no `check()` method. The rule is one pure content transform; the engine derives drift as `apply(current) !== current`, so check and apply cannot disagree by construction.

- Why: the prior-art tools have no check method either (Rector's `refactor()` returns "no change"); a hand-written check can disagree with its apply — the rule reports "satisfied" while apply would still change the file, and CI flaps. Deriving removes that bug class.
- Free generic property test: `apply(apply(x)) === apply(x)` — the engine asserts idempotency over every rule's fixtures with no per-rule test code.
- Dry-run stays structural, not a feature: the pipeline computes the whole plan in memory and `Engine::apply` is the only writer, so `--check` runs every rule's transform without touching disk.
- Every rule carries a mandatory static **description** (what it enforces — feeds the drift report, the docs generation, and the prior-art "description + sample" lesson). A dynamic **`explain(current)`** ("level 5 is below the floor of 6") is opt-in for rules whose drift isn't self-evident from the diff; the computed diff is the fallback.
- Rejected: a mandatory `check()` on the base contract (prior-art lesson 2 read literally) — see above.

### Rule identity = the class name

- Config and disable lists use the FQCN (`PhpStanMinLevel::class`) — refactor-safe, IDE-autocompleted, and no parallel registry of string IDs to keep in sync (rejected: a string-ID registry is a second source of truth).
- Human-facing output (drift report, generated docs) uses the short class name, plus the target path when one class has several instances: `PhpStanMinLevel (projects/ai/phpstan.neon)`.
- Trade-offs, accepted with their fixes:
  - Renaming a rule class breaks consumers' disable lists → a rename is a major version bump; optionally keep a deprecated class alias for one release.
  - One class instantiated several times (a key rule for two keys): disabling by class disables all instances → if a real per-instance case appears, add per-instance identity keyed on class + target path. Don't build it now.

### File-level absence: deferred, kept representable

Content-level enforce-absence (remove a key / line / block) is just another transform and needs nothing special. Whole-file removal is out of scope for now: `ChangeKind` has no delete case and the engine only ever writes.

- Candidate mechanism, the symmetric null: `apply(?string $content): ?string`, where null in = file absent (creation needs that anyway) and null out = file should not exist. **Confirmed at R0**, with the primary justification shifted from future deletion to day-one abstention — see the R0 contract below.

## Decided 2026-07-15 (R0) — the `Rule` contract

Designed on paper against the three probes; R1 builds it. The pre-R0 decisions above stand; where a detail is superseded, its entry says so.

### The contract

```php
interface Rule
{
    /** The file this rule transforms, as ordered path candidates. */
    public function target(): FileTarget;

    /**
     * Pure, idempotent transform from current content to desired content.
     * Null in: the file does not exist. Null out: the file should not exist.
     */
    public function apply(?string $content): ?string;

    /** One line stating what this rule enforces; feeds the drift report and the generated docs. */
    public function description(): string;
}

/** Opt-in seam for rules whose drift is not self-evident from the diff. */
interface ExplainsDrift
{
    /** Why the content drifts, e.g. "level 4 is below the minimum of 6". */
    public function explain(?string $content): string;
}
```

How the engine uses it:

- **The fold.** Group rules by resolved target, then fold each file's rules in declaration order over the current content; one `Change` per file, `Engine::apply` stays the only writer, `--check` stops before writing. Rules never touch the filesystem — the engine reads each file once and passes content in, which is what keeps a rule testable as a plain string-to-string function.
- **`ChangeKind` derives from the fold's endpoints**: null → string is Create, changed string → string is Update, unchanged is InSync. String → null is delete — refused at plan time with a clear error until a delete branch (`ChangeKind::Delete`, a delete-capable `Filesystem` port) exists.
- **Per-rule drift attribution is free.** The fold records each rule's before/after; rule *i* drifted exactly when it changed the running content. The report can name the drifting rules per file (short class name + target, `description()`, `explain()` where implemented) — as informative per rule as hand-written checks would have been, which closes the last gap of the derived-check decision. *(Refined 2026-07-16, first dogfood run: indistinguishable instances — same class, description and explanation, e.g. a same-label override where both rules drift — collapse into one report line with a count. Per-instance origin identity, i.e. which rule set contributed the rule, is deferred; candidate shape when a real need appears: a `--verbose` report naming the contributing rule set.)*
- **`target()` lives on the rule, not in external pairing.** How a rule answers it is its own business: file-specific rules hardcode it (an `.editorconfig` rule cannot be pointed at `phpstan.neon` by construction); only genuinely file-generic rules (`ManagedBlockRule`) take the path as constructor input. Config that pairs paths with rules externally was rejected precisely because it allows that mismatch.

### `FileTarget` — ordered path candidates

Real repos vary their config filenames (`phpstan.neon` vs `phpstan.dist.neon` vs `phpstan.neon.dist`), and the first intended consumer uses a `.dist` variant. So this went into the contract now rather than being deferred: changing the base interface later breaks every rule ever written, and today zero rules exist.

```php
/**
 * The file a rule targets, as ordered path candidates (the tool's own precedence).
 * The engine resolves it to the first candidate that exists, or the first if none do.
 */
final readonly class FileTarget
{
    /** @param non-empty-list<Path> $candidates */
    private function __construct(private array $candidates)
    {
    }

    public static function fromString(string $path): self
    {
        return self::fromStrings($path);
    }

    public static function fromStrings(string ...$candidates): self
    {
        // Path::fromString each; require at least one; reject absolute paths.
    }

    /** @return non-empty-list<Path> */
    public function candidates(): array
    {
        return $this->candidates;
    }
}
```

- **`target()` is a declaration, not a location.** The rule cannot return a resolved `Path`: rules are pure (no filesystem access to check what exists), and one rule instance fans across every configured root, where different candidates may exist — so the resolved path is a property of (rule, root, disk state). It lives on the plan's `Change::path()`, as in the baseline; `apply()` never sees a path at all.
- **Candidates are name variants, not format alternatives (2026-07-16).** One rule's candidates name the same file and format under the tool's different filenames (`phpstan.neon` vs `phpstan.dist.neon`); format alternatives (Symfony `foo.php` / `foo.yaml` / `foo.xml`) are separate per-format rules — see the note under open choice 1. Consequence, held loosely: `ManagedBlockRule` requires all candidates to derive one comment syntax and refuses a mixed list at construction, because `apply()` cannot know which candidate resolved, making per-candidate syntax inexpressible — refusing loudly beats guessing the first candidate. Revisit against a real same-format case that needs differing syntaxes (that would be a per-candidate contract seam). Related known gap: `ManagedBlockRule` creates on absence, so "block into whichever name exists, create nothing" would additionally need an abstain-when-absent construction flag — also deferred until a real case.
- Resolution happens at plan time (the engine owns the filesystem port): the first existing candidate wins; when none exist, the first candidate is the target — which only matters for rules that create, since abstaining rules return null anyway. Rules with different candidate lists that resolve to the same file fold together. *(Superseded 2026-08-05: several existing candidates now resolve by the dist policy — see [the decision](#decided-2026-08-05--resolution-prefers-the-dist-candidate-same-side-ambiguity-refuses); the lone-candidate and creation legs stand.)*
- `fromString()` is the one-element case of `fromStrings()`: one resolution code path, no special case.
- The factories accept strings and parse at the boundary (the codebase precedent: `Path::fromString`, `SyncConfig::withRoots`); the object stores and exposes `Path`. `FileTarget` adds an invariant `Path` alone does not carry: targets must be relative, because they fan across roots.
- Each tool's rule family encodes its candidate list once (a phpstan helper returning the list above in phpstan's own precedence order) — an R3 detail, recorded so nobody re-derives per-tool precedence per rule.

### Symmetric null confirmed — abstention first, deletion later

The pre-R0 candidate is confirmed, with the primary justification changed: **null out is needed on day one, and deletion is the minor use.** The real one is abstention on absent files. `PhpStanMinLevel` on a repo with no phpstan config, or an `ImportRule` whose lone import line would not be a valid config file, must be able to say "no file, no opinion": `apply(null)` returns null, the file stays absent and counts as in sync. With a `string` return type that is inexpressible — returning `''` would create an empty file. Only Tier C block rules create from nothing; Tier A/B rules mostly abstain. *(Corrected at R2: the ImportRule half of that example was wrong twice — a phpstan config holding only an `includes:` section is valid, and the import rule now creates it (see the R2 decision). The abstention capability stands unchanged, with `PhpStanMinLevel` as its first real user: a floor on an absent config has nothing to raise. The fold composes the two when the import rule is declared first — the min-level rule then receives the created content, not null.)* *(Revised 2026-08-04: the floor now creates on absence too — the enforce-over-silence revision in [the PHPStan family record](phpstan-family.md) — leaving abstention a contract capability with no shipped user; it remains correct for custom value-aware rules whose value another mechanism may own.)*

Deletion proper (string in, null out) stays refused until a delete branch exists. And the input `?string` had to be in the contract from day one regardless: widening a parameter type later breaks every implementor, while widening a return type would have been backward-compatible — that asymmetry made this the moment to decide.

### Disabling rules — FQCN, then a predicate; no hash

Consumer-side disabling is not built yet; the mechanism is decided now so the contract needs no retrofit. The ladder:

1. `withoutRule(PhpStanMinLevel::class)` — an FQCN list, the common case: "don't enforce this kind of rule".
2. Class + target path, if instances on different files ever need distinguishing (also the report's identity format).
3. A predicate, for full precision — config is PHP: `withoutRules(fn (Rule $rule): bool => ...)`. It can match on config through the rule's getters, which makes config-sensitivity visible and chosen.

Overriding follows the same seam (recorded 2026-07-17): config is code, so replacing an org rule's config — a custom target location, different import — is `withoutRule(X::class)` + `addRule(new X(...))`; rules stay immutable, nothing mutates an org-owned instance. A rule whose target genuinely varies per project may additionally expose an optional constructor override defaulting to the tool's shared target — build that the first time a real project needs it.

Rejected: matching by a hash of the rule's data (value equality), even as internal machinery behind a readable `withoutRule(class, config)` call. Rules are immutable value objects, so value equality is conceptually sound — but it rots at the wrong moment. A consumer disables a rule because they cannot meet the org minimum yet; that intent is class-level. When the org package raises the minimum from 6 to 7, a value-based match silently stops matching and the rule re-enables itself exactly when the standard got harder — nobody decided that. It also needs a canonical serialization of rule state (reflection over private properties, or an `equals()`/`fingerprint()` on the contract) for a case the predicate covers with zero machinery. Deduplication needs no equality either: folding an identical rule twice is a no-op because apply is idempotent.

### The three probes, and what each proved

- **`ManagedBlockRule`** (Tier C) — the current block engine as one rule: create the file as just the block, replace an existing block in place, or append the block. Proves creation from nothing. Same-label merging (`LineUnionMerger`) moves to rule *construction* inside the block family; the contract is untouched by it. *(Refined at R1: the merger machinery was deleted instead; same-label composition is last-wins via the fold — see the R1 decision below.)*
- **`ImportRule`** (Tier A) — abstains on null, otherwise ensures the import line is present via a targeted insert. Proves abstention and the narrow edit without parse-dump. *(Revised at R2: it creates the config instead of abstaining; abstention's real probe becomes `PhpStanMinLevel`.)*
- **`PhpStanMinLevel`** (Tier B) — abstains on null; reads the configured level; at or above the minimum it returns the content **unchanged**, so the derived check reports in-sync for free; below it, a targeted replace of just that value. Implements `ExplainsDrift`. Proves value-awareness and format preservation. (Renamed from `PhpStanLevelFloor`: the class name says plainly what it does; "floors, not copies" stays as pitch language in prose.)

## Decided 2026-07-16 (R1) — same-label composition is last-wins; the merger machinery is deleted

R1 mapped the baseline onto the contract and hit the one piece that did not carry over: the `ContentMerger` seam (`SingleSpecMerger`, `LineUnionMerger`, `ContentMergerRegistry`), which merged same-label contributions into one block before rendering.

- Half of it is free in the fold: a later same-label `ManagedBlockRule` replaces the earlier rule's block in place, so "child wins wholesale" is emergent behaviour — what `SingleSpecMerger` did, with zero machinery.
- The `.gitignore` line-*union* does not survive the fold (replacement clobbers). Preserving it would have needed a pre-fold coalesce step whose only user was a case with no fixture, no scenario, and no consumer. Deleted with the seam.
- **Union returns opt-in, never as a default flip.** When the block family splits per format (open choice 1), a `GitignoreRule` brings union back as chosen construction behaviour, with an engine-side pre-fold coalesce step as the expected mechanism for cross-set contributions. The same-label default stays last-wins: a consumer relying on last-wins to override a block must not silently start unioning when union arrives.
- Until then, a child set that wants extra lines repeats them or uses its own label. Accepted while pre-release with no consumers: the workaround is config-only and converges on the next sync.
- The planned `ContentMergerRegistry::default()` → `createDefault()` ride-along rename is subsumed by the deletion.

## Decided 2026-07-17 (R2) — the import family is per-tool

"Import" is the family's generic term (the tier is native *import*/extends); the classes are per tool: `PhpStanImportRule` first, later members per tool (`RectorImportRule`, a tsconfig-extends rule, …). The formats proved not format-generic — a neon list entry, a PHP import line and a JSON key are three different edits with three different already-present checks — so the open-choice-1 hedge ("a single rule + small applier where genuinely format-generic") resolves to per-tool classes for this family too.

- Rejected: one generic `ImportRule` + applier registry. The registry's only job would be rediscovering the file type the author already declared in the target, and a free target invites pointing a neon edit at `rector.php` — the mismatch per-tool classes make inexpressible (the same argument that put `target()` on the rule at R0).
- Noted for later, deliberately not forgotten: a generic `ImportRule` convenience on top of the per-tool classes may still come if the tail of tools grows long — build it over several real members, never first.
- `PhpStanImportRule` behaviour: target candidates in phpstan's own precedence (`phpstan.neon`, `phpstan.neon.dist`, `phpstan.dist.neon`), shared via `PhpStanConfigFile::target()` so no phpstan rule re-derives them; absent file → **the config is created**, holding just the import (revised from abstain during the build: enforcing the standard is the point and `withoutRule()` is the opt-out; the created config has no `paths:` — deliberately, the project maintainer owns their own parameters); missing `includes:` section → created at the top of the file (phpstan convention, and prepending disturbs nothing); already-present check = trimmed entry match with surrounding quotes stripped, inside the block-form section only (targeted edit, no parse-dump); an `includes:` in any other form (inline list) is refused at plan time with a convert-to-block-form message; inserted entries copy the section's existing indentation, else the file's detected indent, else a tab (neon's documented default); implements `ExplainsDrift`.
- **The entry mechanics moved to `Formats/Neon/NeonListWriter` (2026-08-04)** — section location, dash-entry scanning with quote-stripped matching (a neon fact: two spellings of one path are the same value), insertion copying entry indentation, creation at the top of the document, and the inline-form refusal. The rule kept what is genuinely phpstan's: the target, the section name, and its messages. This was deliberately *not* held for a second user: the never-first discipline governs creating a *new* abstraction from concrete cases, while the `Formats/` layer is decided, verified architecture (three writers, one cross-family reuse) being applied to a rule that predates it — see the alignment principle in [conventions.md](conventions.md). The future YAML twin (deptrac's `imports:` rule) mirrors `NeonListWriter` as a per-format sibling.
- **Rule library layout (settled with R2):** concrete rules live under a top-level `Rules/` tree — Rector's engine-vs-rules split — grouped per mechanism (`Rules/Block/`, which also hosts the marker machinery) or per tool (`Rules/PhpStan/`). deptrac forbids `Core → Rules`, so the engine provably never references a concrete rule; shared per-tool knowledge sits in the tool's directory (`PhpStanConfigFile`). *(Refined 2026-07-23: one folder per rule inside the group, and mechanism families under `Rules/General/` — see the Rector decision's revision note.)* Text primitives (`Lines::LINE_BREAK` + `split`/`join` as the LF-convention seam, `Indent::TAB`) live in `Core/Text/`; format defaults reference them instead of restating the character.

## Decided 2026-08-02 — org-tier layering of tool imports is additive

How a second-tier org package (one that `include()`s a base package) layers its own tool set on the parent's. Decided for ECS and generalizing to every import rule; pinned by the `Ecs/Family` scenario and exercised by the second-tier test package.

- **Each tier registers its own set; the consumer config carries both entries.** Emergent from existing mechanics, no engine change: the include declares the base tier's rules first, the fold lets the base rule create (or find) the config and the second tier's rule inserts its entry after the base's. The tools' own semantics then deliver the hierarchy: sets register in array order and later registration wins per-checker conflicts, so the second tier overrides the base exactly as declaration order intends.
- **Rejected for now — the nested shape**: the second tier's set file imports the parent set *inside itself*, and the consumer registers only the second tier's entry. Cleaner-looking consumer config, but it needs two things that don't exist yet, recorded here for when an org genuinely wants to hide its tier structure from consumers:
  1. Suppressing the base tier's import rule from within the second-tier package — that is the `withoutRule()` disable ladder, decided at R0 but never built. Note the recorded per-class semantics: disabling by class would remove the second tier's own instance too, so this case likely forces the per-instance identity (class + config) the R0 entry deferred.
  2. A robust parent-set path *inside* the set file: a cwd-relative path (`vendor/<parent>/config/ecs.php`) only resolves while the tool runs from the project root, and a vendor-sibling `__DIR__` walk (`__DIR__ . '/../../<parent>/config/ecs.php'`) breaks under symlinked path-repo installs, where `__DIR__` resolves outside the consumer entirely. The install-location resolution layer (next decision) is the proper mechanism; nesting should wait for it.
- Trigger to revisit: an org that wants consumers to see a single entry / not know the tier structure, or a tier that must *replace* (not extend) the parent's set.

## Decided 2026-08-02 — install-location resolution: a root-aware layer, deferred

*(Superseded the same date by the revision below: the layer was built as config-build-time self-location, without the per-root seam — which stays parked with its trigger recorded in the revision.)*

The base-set params and the phpstan ruleset param declare consumer-root-relative paths that assume where the org package is installed (`vendor/<package>/…`). Discussed to its end during the ECS build; the direction is decided, the build deliberately deferred until after the ECS family ships.

- The facts: composer installs a package only ever at `<vendor-dir>/<package-name>` — the vendor-dir is the sole variable — but the engine itself only requires the org package to be *autoloadable*, not vendor-installed: a psr-4-mapped in-repo package works today, so install locations are genuinely free. A single-layout org declares its true path, whatever that layout is; what a declared path cannot express is one org package serving several layouts at once.
- **The direction: a resolution layer.** The org package locates itself at config-build time — `__DIR__` in its own class resolves in every layout (vendor copy, symlink, in-repo psr-4), no composer metadata needed — and a plan-time seam relativizes per root: the org declares a root-parameterized rule *factory*, the engine evaluates it per root, and the factory returns an ordinary pure rule carrying the computed entry. The `Rule` contract stays untouched, and the mechanism covers neon includes exactly as well as PHP entries — one uniform answer for all tool families, correct at every sync in any layout.
- **Accepted trade-off, explicitly:** a recomputed entry can leave its stale predecessor behind (the format writers are add-if-absent, and a lingering dead path makes ECS and phpstan refuse to run). Accepted because a sync's diff is always reviewed manually before it lands, and the R4 state file can later clean stale entries up as a bonus — provenance is exactly what R4 adds.
- Considered along the way:
  - Splitting the param into package + in-package path: cosmetic — the vendor assumption moves into the rule instead of going away. Rejected.
  - Runtime constant references (the tools' own SetList pattern: the org ships a path-constants class, the rule writes the inline FQCN, PHP re-resolves it on every tool run): the written entry never goes stale and no engine machinery is needed — but it only exists for PHP-config tools (neon has no runtime to late-bind in), splitting the family mechanisms. Set aside in favour of the uniform layer; remains the fallback if the layer disappoints.
  - `phpstan/extension-installer`: the neon ecosystem's own resolution (auto-include at composer dump time), composer-installed consumers only. Recorded as the tool-native alternative for phpstan.
- Until the layer lands, the params stay declared consumer-root-relative paths; a consumer with a deviating layout overrides via `withoutRule()` + `addRule()`.

### Revised 2026-08-02 (built) — config-build-time self-location; the Authoring layer

Built the same date, and simpler than the direction above: no per-root seam, no rule changes — the org package is located **once at config-build time** and the rules receive ordinary consumer-root-relative strings.

- **The mechanism.** A new `Authoring/` layer (config-build-time support, outside the pipeline like template reading always was) ships two classes. `Package` is the org package *as installed in the consumer*: `read()` loads distributed content (absorbing `TemplateDirectory`), `path()` renders the consumer-root-relative reference; both resolve inside the package's `templates/` directory, which makes the authoring rule "never point a rule at the package's own config" structural. `Standard` is the base rule set an org ships: its constructor runs `enforce($package ?? Package::fromClass(static::class))`, so a subclass holds nothing but rule declarations; tests and deviating layouts inject via `new TheirStandard(package: new Package(directory, installedAt))`.
- **Self-location asks composer, not the filesystem.** `Package::fromClass()` walks from the class file to the nearest composer.json only to learn the package *name*; the *location* comes from `InstalledVersions::getInstallPath()`, canonicalized textually (never `realpath`) and relativized against the working directory. The decisive fact, verified in the symlinked test consumer: PHP resolves symlinks in `__FILE__`/`__DIR__`, so under a composer path-repo install the class file resolves outside the consumer entirely, and no filesystem operation can recover the vendor alias from the resolved path — composer's install record is the only surviving source of the portable `vendor/<name>` spelling (`install_path` is recorded vendor-anchored even for symlinked installs). This amends the earlier "no composer metadata needed" clause, deliberately: the cost is a `composer-runtime-api: ^2.1` require, which installs nothing — the class ships in every vendor directory this tool can run from.
- **Why the entry must be the vendor spelling:** the computed path is frozen as text in the consumer's committed config. A resolved path (`../<sibling checkout>/…`) is a machine-local fact that breaks every other clone and CI; `vendor/<name>` is true on every machine composer installs to, whether as a real copy or a symlink.
- Considered and set aside, in the order the discussion ran:
  - **Pure `__DIR__` + textual relativization** (symfony `Path::makeRelative` has the math): writes the machine-local spelling under symlinked installs — exactly the dogfood layout.
  - **A config-build disk probe of `vendor/<name>`**: avoids the composer class but re-implements a sliver of composer's knowledge, hardcodes the vendor-dir name, and couples config-build to disk state that in-memory test syncs do not share.
  - **Declaration with a convention default** (an `InstallLocation::vendor('<name>')` the consumer can override): fully deterministic and composer-free, and the near-winner — but every mechanism's output is the same frozen text, so once the composer-dependency objection was withdrawn (nothing is installed), discovery through the actual authority won. The consumer-side `package:` injection survives as the override for genuinely deviating layouts (in-repo psr-4 packages).
- **The per-root factory seam above stays parked**, trigger unchanged: the first real consumer with sync roots below the project top (central-vendor monorepo). Until then the location is resolved once against the working directory, and each root is its own consumer project.
- **Root-package rendering:** in the org package's own repo (its test suite) the org *is* composer's root package, so references render bare (`templates/…`); org tests inject a `Package` when they want consumer-realistic assertions.
- Correction to the nested-shape note under the org-tier layering decision: a robust parent-set path *inside* a set file is a tool-runtime concern this sync-time layer deliberately does not serve; if the nested shape is ever built, the candidate mechanism is `InstalledVersions::getInstallPath()` evaluated inside the set file itself.
- **One distributed directory: `templates/`** (decided with this build). The shipped rulesets move from the org packages' `config/` directories — which had drifted in with the R2/R3 tool families without a recorded decision — into `templates/`, restoring the authoring guide's single-home rule for distributed content. Consumer-visible references read `vendor/<name>/templates/…`. A configurable distributed-directory name is noted for later as a `Package` construction knob, built when a real package needs it.
- **Naming**, by the artifact-noun doctrine: `Package`, `Standard`, `enforce()` — an org class reads as the docs talk ("the org package is the standard"; a standard states what it enforces), and `fromClass()` follows the `from<Source>` factory convention (a bare `locate()` would be the novel factory name the conventions forbid). Rejected: `InstalledPackage`/`OrgPackage` (the qualifier earns nothing inside the authoring namespace — the `Path`/`Label` precedent), `PackageRuleSet`/`OrgRuleSet` (mechanism suffix), `define()`/`declare()` (read as PHP builtins), `compose()`/`configure()`/`ship()` (weaker fits recorded with the decision).

## Flagged 2026-08-04 — multi-file config resolution (dist + local overrides)

`FileTarget` resolution is first-existing-candidate (R0). For the override-pattern tools (phpstan, psalm, php-cs-fixer, phpunit: the non-dist file, when present, replaces the dist file entirely — no merge), a repo carrying both a committed `.dist` config and a local, often gitignored override resolves to the local file — the sync would write the standard where it reaches neither the repo, CI, nor other clones. The committed dist file is where the standard belongs, yet the tool reads the local file when present, so a dist-only standard is locally overridable by construction: both answers are wrong in one dimension, which is why this needs its own design pass rather than a quick fix. Interim candidate, per the fail-loud doctrine: plan-time refusal when more than one candidate exists (the inline-`includes:` precedent), upgradeable to a policy later. Genuine multi-file *merging* (docker-compose's `compose.override.yaml`) is rare in the current tool families and out of scope until such a tool arrives. Design after the psalm build.

*(Decided 2026-08-05 — see the decision below. The interim refusal was never built; the design pass went straight to the policy.)*

### Decided 2026-08-05 — resolution prefers the dist candidate; same-side ambiguity refuses

The design pass the flag called for. The finding that settled it: first-existing resolution does not just pick a debatable file — it makes the plan **machine-dependent**. In a repo carrying a committed `phpstan.neon.dist` and a gitignored local `phpstan.neon`, a local sync writes the standard into the personal file (`git diff` shows nothing — the file is gitignored, and a floored local level is clobbered on the way), while CI `--check` still fails because the dist file never changed: local sync and CI check disagree about the same repo. Affected wherever a target has dist candidates: phpstan and psalm (three candidates each), rector (`rector.php` / `rector.dist.php` — the flag did not name it, but its resolver is the same override pattern), the future php-cs-fixer and phpunit families, and any org-declared `ManagedBlock` target with a dist variant; ECS is untouched (single candidate).

- **The policy.** No candidate exists → create the first (unchanged). Exactly one exists → sync it, whatever its name (unchanged — the dominant single-`phpstan.neon` repo). One dist and one non-dist exist → **the dist variant is the sync target**: the dist naming convention has one universal meaning — the dist file is the committed home, and the non-dist name exists precisely so an uncommitted file can shadow it, which is the only reason a repo carries both. The standard lands in the committed file, the diff is reviewable, the local file stays the developer's business, and local sync agrees with CI byte-for-byte.
- **Same-side ambiguity refuses at plan time** — more than one existing dist variant (`phpstan.neon.dist` + `phpstan.dist.neon`) *or* more than one existing non-dist variant. Widened deliberately from the proposal's dist-only refusal, so both sides are covered: two files on the same side of the convention are a confused repo, not a workflow, and even where the dist preference could technically still resolve (several non-dist files beside one dist), the passed-over-file note below could not name a single shadowing file — fail-loud is the doctrine. Resolution therefore proceeds only with at most one existing file per side, leaving three live shapes: dist alone, non-dist alone, one of each (dist wins). Plain `RuntimeException` like the existing plan-time refusals; this does not unpark the refusal-exception decision in [conventions.md](conventions.md).
- **Dist-ness derives from the name, not a declaration**: a candidate is a dist variant when its filename carries a dotted segment exactly `dist` (`phpstan.neon.dist`, `psalm.dist.xml`, `.php-cs-fixer.dist.php`, `phpunit.xml.dist`). Safe because the classification only takes effect when several candidates exist on disk, and it means org-declared `ManagedBlock` targets get the policy with zero new authoring API; the convention is already engine knowledge — `MarkerSyntax` detection walks extensions right to left precisely so the `dist` suffix does not hide the real type. This is not the R2 "registry rediscovers declared knowledge" smell: nothing is declared today, and the `.dist` segment is the pattern's defining artifact. Rejected: explicit per-candidate roles on `FileTarget` — every declaration site restating what the name already says.
- **A passed-over non-dist file is reported, never silent**: the plan note reads along the lines of "phpstan.neon exists and replaces phpstan.neon.dist for tool runs; the standard was synced to the dist file". This is the honest answer to the flag's "locally overridable by construction" dimension — the sync cannot change the tool's own semantics (the local file is the escape hatch the tools designed), but it never lets the shadowing pass silently. The wording is deliberately pattern-agnostic, so the odd repo that *commits* both files sees the same true sentence every run. Mechanically the fact rides on `ResolvedTarget`; resolution already discovers it — the only added cost is scanning the full candidate list instead of stopping at the first hit.
- **Creation stays on the first candidate** (the non-dist name). A repo that wants the dist pattern renames once; a lone dist file resolves normally from then on.
- Rejected, in the order considered:
  - **Plan-time refusal whenever more than one candidate exists** — the interim the flag itself proposed. It fires only on developer machines (CI sees one file), so it blocks local sync for exactly the legitimate override workflow, the only fix its message could offer is deleting the developer's own file, and the machine-dependence survives as local-refuses-CI-passes. With the policy decidable now, shipping the stopgap first is work replaced immediately.
  - **Sync every existing candidate** — enforces the standard on local runs too, but edits a gitignored personal file (invisible to any review — the reviewed-diff assumption the install-location decision leans on), reverts the developer's deliberate deviation, inserts a duplicate org include beside the local file's own dist include (transitive includes are invisible to the entry match), and grows one-target-many-changes machinery. The cost lands on exactly the legitimate pattern.
  - **Asking git which file is tracked** — the actual definition of "committed home", but it needs a VCS port the pure-filesystem engine deliberately lacks, and the name convention gives the same answer without one. The residual this leaves, accepted: a repo whose *only* config is a gitignored local file is indistinguishable from a normal single-file repo, and sync writes there.
  - **Sync the dist file + check-only on the local file** — would flag local drift without touching the personal file, but produces false drift by construction: a proper local override inherits everything through its dist include, which value-aware rules cannot see without cross-file include semantics — the universal-merge non-goal in miniature.
- Genuine multi-file *merging* (docker-compose's `compose.override.yaml`) stays out of scope until such a tool family arrives, as flagged.
- **Build scope (pending):** `Engine::resolveTarget()` gathers all existing candidates and picks per policy; the dist classification on `FileTarget` (or `Path`); `ResolvedTarget` carries the passed-over fact; the report renders the note. Scenario fixtures per the behaviour-catalog rule: dist + local resolving to the dist file (phpstan as the representative family — resolution is engine-level), both refusal cases, and the note; the multi-non-dist refusal is only expressible via a `ManagedBlock` target today, since no tool family declares two non-dist names. Slots anywhere relative to the composer.json family — nothing there waits on this (composer.json is single-candidate).

**Built 2026-08-06.** `Path::isDistVariant()` (a dotted segment exactly `dist` in the final path component — directories named `dist` do not count), the resolution partition in `Engine::resolveTarget()` with the two same-side refusals, and `ResolvedTarget`/`Change` carrying the shadowing file into the report. *(Refined the same date, from review — the dist knowledge had smeared across general types: the classification moved off `Path` (a general filesystem value carries no config-naming convention) and the policy out of `Engine` into a dedicated `Core/Engine/TargetResolver` owning the whole convention — the `dist` segment constant, the partition, both refusals, the preference — with `Engine` back to collect–resolve–fold orchestration; `ResolvedTarget::shadowedBy()`/`Change::shadowedBy()` are documented as the general concept (an existing candidate the tool reads in preference to the resolved file), the dist story living only in the resolver and the report sentence; `DriftReport` renders notes through a general `notes()` seam whose single kind is the shadowing note — a plan-level note mechanism waits for a second kind per never-first, plausible trigger: the parked refusal-as-report-entry decision in [conventions.md](conventions.md). ## Agreed 2026-08-04 — enforced comments on synced values (later phase)

An opt-in `comment:` on value-writing rules, written with the enforced value and **enforced like it**: a missing, edited, or replaced comment is drift and is rewritten, so a project that lowers a floored value and re-annotates it sees value and prose revert together in one reviewed diff. It answers the `Write`-default's one weak spot — the written line explains itself, in the file and in the diff ("minimum level — raise freely; lowering is reverted on sync"). Leaning: a trailing comment on the enforced line, one unit in file and diff. Open questions parked for the design phase: rules that write multiple lines; per-format viability (neon/yaml `#` and PHP `//` trail fine; XML cannot hold a comment inside a tag next to an attribute); and reconciling with the floor's current behaviour of *preserving* a project's own trailing comment, which inverts to *owning* that spot for rules that opt in. A project keeps its own annotations on the lines above — only the enforced line is owned. Reordered 2026-08-04: designed and built *before* the psalm build (after the neon cleanup), so the written floor reaches consumers already explained.

**Decided and built 2026-08-04.** The parked questions, resolved:

- **The comment is enforced whenever configured, compliant values included** — one rule, no sub-cases: a configured comment means the line is org-annotated, so a stricter-than-floor `level: 8` gains the comment too, telling the maintainer the floor exists *before* they trip it. Rejected: attaching only to lines the rule writes (avoids a one-time comment-adding diff on compliant configs, but leaves exactly those maintainers unexplained until they first drift).
- **Preserve when unconfigured, own when configured** — the recorded reconciliation: rules without a comment keep today's behaviour (a project's trailing comment survives every replace, pinned by the existing fixtures); a configured comment owns the spot, and a project's replacement annotation reverts together with any value drift in one reviewed diff.
- **Mechanics:** `NeonScalarWriter::write()` gained the optional comment (enforced on replace and carried into created lines and configs), and a new `ensureTrailingComment()` annotates a compliant line while keeping the value text verbatim — `max` stays `max`, a quoted spelling stays quoted. The canonical separator is ` # `; comparison is text-exact, so a deviating spelling normalizes.
- **Comment text:** org-authored free text, one non-empty line, refused at rule construction; content is otherwise free (the quote-aware comment boundary handles `#` inside values).
- **The XML verdict: no comment support** — an XML attribute has no inline position that reads as that attribute's comment, so the psalm family ships without; `ExplainsDrift` and the generated rule catalog carry the explanation there. Multi-line-writing rules (base configs, skeletons) are likewise out of scope — the comment is a property of one enforced line.
- **First adopter: `PhpStanMinLevel`** (param `comment:`), the line that motivated the feature. Pins would need per-leaf comments (a `PinnedValue` extension, its own small design), list and fluent entries need `# `/`// ` support in their writers — all adoptable later on this pattern. ## Open choices — settled at R0 (2026-07-15)

1. **Split "what" from "how", or self-contained per-format rules?** The cleaner answer: instead of one generic `ManagedBlockRule` plus a separate apply-strategy, have **per-format rule classes** — `EditorConfigRule`, `GitignoreRule`, … — each self-contained, baking its format knowledge in (sharing a common `AbstractBlockRule` for the marker mechanics). The format-specific class *is* the "how", so no separate strategy layer or `applicable()` pairing is needed, and it grows well — a contributor adds a `FooRule` for a new format. Caveat: for format-*generic* families (an `ImportRule` that varies only by a small syntax detail across `phpstan.neon` / `rector.php`), N per-format classes are overkill — there a single rule with a tiny format-applier is lighter. **Decided:** per rule *family* — per-format classes for the block family (resolves the split cleanly); a single rule + small applier only where a family is genuinely format-generic. Note `.editorconfig` and `.gitignore` currently do identical block-placement, so they can start on one shared base and split when real format-specifics appear (editorconfig key-merge, gitignore line-union).
   **Extended 2026-07-16 — multi-format config, rule families, and the block-format guard.** One concern across config formats (Symfony `foo.php` / `foo.yaml` / `foo.xml`) = one rule per format, each abstaining while its file is absent (the symmetric null), so the repo's chosen format is acted on and the others stay silent; the org package decides which format's rule creates when none exist. Declaring the same values per format would drift and a format could be forgotten, so a *family factory* declares the config once and returns the per-format rule set. A first-class rule-family concept between `RuleSet` and `Rule` is deferred until factories prove insufficient (family-level disabling or reporting would be the trigger). The what/how split stays rejected; the guard against invalid pairings is that the block family refuses formats it cannot mark: `json` (no comments at all) and `xml`/`html` (only enclosed `<!-- -->` comments — the marker grammar draws comment-*lead* lines, and for xml the generic block mechanics are structurally wrong anyway: create-from-nothing yields a rootless fragment, append-at-end lands after the root close tag, so structured rules are the right tool there). Unknown extensions keep the hash default, because opaque-text co-management is an open set (`.editorconfig`, `.gitignore`). Expected trigger for enclosed-comment support: managed README sections — markdown uses `<!-- -->` markers and append-at-end is valid there; that adds a comment *tail* to the marker grammar, and formats then leave the refusal list case by case.
2. **Ordering.** Rules can share a file. A global integer priority is the known pain point. **Decided:** the fold runs in declaration order (rule-set composition order, matching the block engine's later-wins precedence). Idempotent rules on disjoint concerns make order irrelevant; where rules genuinely overlap, declaration order is the deterministic tiebreak. No priority integer, no dependency graph.
3. **Config shape.** **Decided:** typed constructor parameters (`new PhpStanMinLevel(minLevel: 6)`) — the rule *is* immutable config + behaviour, which satisfies the prior-art "typed / validated" lesson without a separate seam. Adopt a `ConfigurableRule` seam or self-describing schema only if a rule's config gets rich.
4. **Removal vs disabling vs un-applying a dropped rule** — three distinct things, worth keeping apart:
   - **Disable a rule** = stop enforcing it: do nothing, and leave whatever is already in the file untouched (matches every prior-art tool — non-registration / `severity=0`). No provenance, no undo.
   - **A "remove" rule** = a rule whose `apply()` enforces *absence* (delete a key / line / block if present, no-op if not). This is a first-class, idempotent operation — enforce-absence is just the mirror of enforce-presence — and needs no provenance.
   - **Un-applying a *dropped* rule** = undoing the past effect of a rule no longer configured at all. *This* is the hard one that needs provenance (a state file), because nothing in the config still describes what to undo.
   Note: disabling a parent rule stops it *re-adding* its content but does **not** clean up what it already added — deleting that is a separate "remove" rule (or dropped-rule undo). **Decided:** enforce-presence + enforce-absence rules are plain transforms (nothing special needed); consumer-side disabling follows the ladder in the R0 contract (FQCN list, then a predicate — no hash); dropped-rule undo (state file) stays deferred until manual cleanup is a burden. Whole-file removal is the refused null output — see the R0 contract.

## Testing rules

Carry the fixture discipline forward from the block engine: each rule ships a **before/after sample**, which doubles as its test fixture (Rector refuses to define a rule without one). Concretely, the existing scenario suite (`input/` → `expected/` fixtures synced and asserted) becomes **per-rule fixtures** — one small before/after case per behaviour the rule has (from-scratch, already-satisfied/idempotent, and value-aware edges like "already higher, leave it"). The rule is the unit; its fixtures are the behaviour catalog and the worked examples for consumers. Any change to a rule's behaviour adds / updates / removes its fixture.

**The rule catalog docs are generated from the fixtures (decided 2026-07-15).** The unit of documentation is the *scenario*, not the rule: the generator renders each rule's description plus **all** its scenarios as before/after pairs — unlike Rector's single code sample, which often can't show a rule's whole point. Required shape: each scenario's kebab-case directory name becomes its example heading; an optional one-line caption file covers cases where the name isn't enough. One source feeds tests and docs, so neither can rot alone. The generator itself is part of the docs phase, but the fixture shape is binding now so nothing needs restructuring later.
